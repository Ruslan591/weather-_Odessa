# Совместная работа ChatGPT и Claude

## Цель

Этот файл является общей инструкцией для ChatGPT и Claude при работе
над репозиторием weather-_Odessa.

Цель — совместно развивать проект без потери контекста, конфликтов
и случайного изменения работающих частей системы.

---

## Репозиторий

GitHub: `Ruslan591/weather-_Odessa`

Проект включает:

- сайт прогноза погоды для Одессы;
- GitHub Pages;
- VPS Oracle Cloud;
- погодные модели Open-Meteo;
- EUMETSAT спутниковые данные;
- SYNOP и BUFR;
- фронтальный анализ;
- AI-анализ прогнозов;
- генерацию прогнозного видео;
- автоматические VPS-пайплайны.

## Роли AI

### ChatGPT

Основные задачи:

- анализ архитектуры проекта;
- поиск ошибок и причин проблем;
- проверка логики алгоритмов;
- анализ погодных данных;
- проверка изменений Claude;
- постановка задач;
- ведение технического контекста;
- координация работы между AI.

ChatGPT НЕ должен предполагать, что изменение работает,
без проверки кода, логов или фактического результата.

---

### Claude

Основные задачи:

- реализация изменений в коде;
- редактирование файлов;
- работа с VPS;
- выполнение команд;
- тестирование изменений;
- исправление найденных ошибок.

Перед внесением крупных изменений Claude должен:

1. Прочитать актуальные инструкции в `docs/topics/`.
2. Проверить связанные файлы.
3. Понять существующую архитектуру.
4. Не заменять работающую систему упрощённой версией.

## Обязательные правила

### 1. Не ломать существующий проект

Запрещено:

- переписывать большие части системы без необходимости;
- заменять существующую логику заглушками;
- удалять функции без проверки зависимостей;
- создавать дублирующие параллельные системы;
- менять структуру репозитория без причины.

Если возможен минимальный патч — использовать минимальный патч.

---

### 2. Не делать приблизительных исправлений

Нельзя исправлять проблему предположением.

Необходимо:

1. определить фактическую причину;
2. проверить входные данные;
3. проверить код;
4. проверить логи;
5. только после этого менять код.

---

### 3. После изменения обязательно проверить результат

После изменения Claude должен сообщить:

- какие файлы изменены;
- что именно изменено;
- почему это было изменено;
- как проверялось;
- результат проверки;
- возможные риски.

---

### 4. Не менять проект без явной необходимости

Особенно осторожно работать с:

- `.github/workflows/`;
- VPS cron;
- `vps_pipeline.py`;
- `vps_satellite_pipeline.py`;
- `vps_ai_pipeline.py`;
- GitHub Pages;
- Open-Meteo запросами;
- EUMETSAT API;
- существующими JSON-файлами;
- системой AI-очереди.

## Обмен информацией между AI

Для каждой значимой темы использовать отдельный файл:

`docs/topics/`

Примеры:

- `OPEN_METEO.md`
- `EUMETSAT.md`
- `FRONTS.md`
- `VPS.md`
- `AI_PIPELINE.md`
- `GITHUB_PAGES.md`

Каждый AI перед началом работы должен прочитать
файл соответствующей темы.

После существенного изменения необходимо обновить
соответствующий файл.

## Формат записи о проблеме

**Проблема**

Краткое описание.

**Фактические симптомы**

Логи, ошибки, наблюдаемое поведение.

**Причина**

Подтверждённая причина.

Не писать предположение как факт.

**Решение**

Что изменено.

**Проверка**

Какие команды или тесты были выполнены.

**Результат**

Что получилось после изменения.

**Статус**

- работает;
- требует наблюдения;
- не исправлено;
- требует решения пользователя.

## ОБНОВЛЕНИЕ ПРОТОКОЛА | 2026-09-10T05:43:03Z UTC

GPT в текущем GitHub-подключении имеет доступ **на чтение** репозитория,
но **не имеет права записи** (`403 Resource not accessible by
integration`).

До отдельного изменения доступа действует следующий рабочий порядок.

### 1. Claude ведёт AI_DISCUSSION.md за обе роли

Claude самостоятельно коммитит в `docs/ai/AI_DISCUSSION.md`:

- свои записи с ролью `CLAUDE`;
- результаты review, полученные от GPT, с ролью `GPT`.

GPT не должен требовать от USER ручного копирования своих review в файл.

### 2. Формат GPT-записи

Когда USER передаёт Claude текст review/решения GPT, Claude добавляет
его в журнал **без изменения технического смысла**:

```
### GPT | <UTC timestamp> | TASK <TASK_ID> | <STATUS>

<review GPT>

*(запись добавлена Claude в AI_DISCUSSION.md, так как GPT имеет
read-only GitHub access)*
```

Допускается исправить только очевидные опечатки или форматирование.
**Нельзя** самостоятельно менять вывод GPT с "REQUEST CHANGES" на
"APPROVE", удалять замечания или сокращать технические требования.

### 3. Обязательная последовательность работы

Для каждой задачи:

1. GPT/Claude фиксирует анализ.
2. Claude публикует Proposal в `AI_DISCUSSION.md`.
3. GPT делает review.
4. Claude записывает результат GPT review в `AI_DISCUSSION.md`.
5. Если **REQUEST CHANGES**: Claude исправляет Proposal → публикует
   новый Proposal → ожидает следующий review.
6. Если **APPROVE**: Claude вносит изменения в код → публикует
   `IMPLEMENTED` → обязательно указывает **commit SHA, Changed, Tests,
   Risks**.
7. GPT делает implementation review по фактическому diff/коду.
8. Claude записывает implementation review GPT в `AI_DISCUSSION.md`.
9. Только после итогового **APPROVE** задача считается завершённой.

### 4. Нельзя писать APPROVED задним числом

Claude не должен писать, например, «Proposal v3 (APPROVED)», если явная
запись GPT "APPROVE" фактически отсутствует в журнале. Статус должен
соответствовать реально зафиксированному решению GPT.

### 5. Принцип

`AI_DISCUSSION.md` — единый журнал принятия технических решений. Если
GPT не может записать решение непосредственно в GitHub, Claude является
техническим редактором журнала и фиксирует решение GPT от имени роли
"GPT". USER не должен выполнять роль ручного копировщика между AI.

commit SHA, результаты тестов. Не копировать полный текст review, не
пересказывать подробно.

Формат GPT review:
```

Required:
- пункт 1
```
или
```
### GPT REVIEW | Proposal vX | STATUS: APPROVE
Approved for implementation.
```

Формат ответа Claude:
```
PROPOSAL vX
Changes:
- ...
Algorithm:
- ... (не повторять архитектуру, если не изменилась)
STATUS: awaiting GPT review
```

После APPROVE: реализация → тесты → commit+tests в decision log → GPT
implementation review → живой Europe overlay + visual review.
