#### Анализ текущей реализации

Прочитан `scripts/open_meteo_frontal_confirm.py` (462 строки) целиком + рендер
`nearby_precip.js`.

**Backend (`detect_europe_fronts`, строки ~247–270):**
- Сетка 220км по объединённому bbox far∪very_far (не повёрнутая, шаг в
  градусах, не в км — на 33–60°N физическая длина шага по долготе
  меняется почти в 1.7 раза север/юг, это отдельное наблюдение, не
  трогаю в этом Proposal).
- На каждую модель: `front_like = (|∇temp| > 3.0°C) OR (|∇pressure| >
  1.5 гПа)` через `np.gradient` по индексам сетки (булево, не
  непрерывное поле).
- Консенсус: `votes >= 3` из 5 моделей → `confirmed=True`.
- **НЕТ** подавления немаксимумов, **НЕТ** связывания соседних точек в
  сегмент — каждая подтверждённая ячейка сетки публикуется независимо.

**Frontend (`nearby_precip.js::_buildEuropeOverlaySvgInner`, строки
803–812):**
- Для каждой точки `overlayData.points` рисуется независимый
  `<circle>` (зелёный r=4.5 если confirmed, иначе янтарный r=2.5). Связи
  между точками нет вообще — то, что бэкенд считает "подтверждено",
  на карте физически не может выглядеть иначе, чем набором кружков.

**Вывод:** проблема в ДВУХ местах, а не в одном: (1) детектор помечает
все точки с высоким градиентом без различения "широкая зона" vs "узкий
фронт", (2) даже если бы детектор был идеален, фронтенд всё равно рисует
только точки — линия нигде не строится программно.

#### Proposal (минимально инвазивный, только внутри
`open_meteo_frontal_confirm.py` + один рендер-метод в `nearby_precip.js`)

**Backend:**
1. Заменить булево `front_like` OR-условие на непрерывный
   frontal-intensity score на модель:
   `score = max(grad_t / EUROPE_TEMP_GRAD_THRESHOLD, grad_p / EUROPE_PRESSURE_GRAD_THRESHOLD)`
   (нормировано к порогу = 1.0 → сохраняет пороги, но даёт непрерывное
   поле для шага 2).
2. Усреднить score по моделям, входящим в консенсус (>=3 голосов "score
   >= 1.0") → единое поле `consensus_field[rows,cols]`.
3. **Non-maximum suppression**: для каждой ячейки, прошедшей порог,
   оставить её только если это локальный максимум среди 8 соседей по
   `consensus_field` (простой `scipy.ndimage.maximum_filter` 3x3, без
   scipy — вручную по массиву; сетка маленькая, ~10-15 x 15-20 ячеек,
   производительность не проблема). Это превращает "широкую область" в
   тонкий гребень толщиной в 1 ячейку.
4. **Связывание в сегменты**: BFS/DFS с 8-связностью по
   NMS-отфильтрованным ячейкам → список `segments`, каждый — упорядоченная
   цепочка точек (сортировка внутри сегмента по проекции на первую
   главную компоненту координат сегмента — просто и достаточно для
   сеток такого размера, полноценный PCA не нужен, хватит сортировки по
   доминирующей оси bbox сегмента).
5. Записывать в `europe_frontal_overlay.json` **дополнительное** поле
   `"segments": [{"id", "px_far": [[x,y],...], "px_very_far": [[x,y],...],
   "avg_score"}]` — существующее поле `"points"` НЕ убирать (обратная
   совместимость с уже задеплоенным фронтендом на время миграции).

**Frontend (`_buildEuropeOverlaySvgInner`):**
6. Если `overlayData.segments` присутствует — рисовать `<polyline
   points="x1,y1 x2,y2 ..." stroke="#3cdc3c" stroke-width="2"
   fill="none"/>` на сегмент вместо кружков по всем точкам. Fallback на
   старый point-by-point рендер, если `segments` нет (не ломает текущий
   прод при частичном деплое).

### CLAUDE | 2026-09-09T21:21:22Z UTC | TASK EUROPE_FRONT_LINE_001 | PROPOSAL v2 (ответ на REQUEST CHANGES)

Принимаю все 5 пунктов. Отдельно — по REQUEST (centerline без NMS/PCA/scipy):

#### Алгоритм: graph-diameter path вместо NMS + PCA

Убираю отдельный шаг NMS полностью — вместо "прорядить сетку, потом
связать" делаю "связать всё как есть, потом извлечь тонкую линию из
готового графа связности". Это снимает риск п.1 (NMS ничего не рвёт,
потому что его больше нет как отдельного шага над сырыми ячейками).

1. **Connected components** — как согласовано, BFS/DFS 8-связность по
   confirmed-ячейкам (`n_valid >= MIN_MODEL_VOTES`), без предварительного
   прореживания. Компонент может быть "толстым" (широкая зона) — это
   нормально на этом шаге.
2. **Отбросить компоненты `size < MIN_COMPONENT_CELLS` (3)** — как
   согласовано.
3. **Centerline = диаметр графа компонента** (стандартный приём "double
   BFS/Dijkstra", без scipy, только `heapq` из стандартной библиотеки):
   - вес ребра между 8-соседями = евклидово расстояние в шагах сетки
     (1.0 для орто-соседей, √2 для диагональных) — чуть точнее, чем
     просто число хопов, на изогнутых линиях с диагональными шагами;
   - шаг A: из произвольной ячейки компонента запустить
     Dijkstra/BFS → найти самую удалённую ячейку `P1`;
   - шаг B: из `P1` запустить Dijkstra/BFS ещё раз → самая удалённая
     ячейка `P2`, с восстановлением пути по parent-указателям;
   - путь `P1 → P2` — это и есть centerline. Это математически гарантированный
     "диаметр" графа компонента (стандартное свойство: для дерева/
     произвольного связного графа с неотрицательными весами два прохода
     BFS/Dijkstra от произвольной точки находят одну из двух самых
     дальних друг от друга точек).
4. **Почему это чинит оба риска из REQUEST:**
   - *"не разрывает прямую линию из соседних ячеек"* — если компонент
     сам по себе есть прямая цепочка соседних ячеек (путь без ветвлений),
     диаметр графа == вся цепочка целиком, ни одна ячейка не теряется.
   - *"корректнее PCA на изгибах"* — путь строится по фактическим рёбрам
     графа (реальная связность ячеек), а не по проекции координат на
     одну ось. На изогнутом фронте (дуга, S-образная кривая) PCA-ось даёт
     одну прямую и путает порядок точек в изгибе; диаметр-путь идёт вдоль
     самой кривой, порядок всегда корректный.
   - *ветвление (T-образная структура)* — диаметр-путь автоматически
     выбирает ГЛАВНУЮ линию (два самых удалённых конца), короткие боковые
     ответвления в путь просто не попадают. Ячейки компонента, не попавшие
     в centerline, не выбрасываются из данных — они остаются видны через
     существующее поле `points` (fallback-рендер), просто не превращаются
     в отдельный `segments`-элемент.
5. **Производительность** — компоненты на сетке 220км по объединённому
   bbox far∪very_far малы (весь grid ~266 точек, отдельный компонент
   заведомо меньше), два прохода Dijkstra через `heapq` — O(N log N) на
   компонент, для N~20-40 это доли миллисекунды. Scipy не требуется.

#### Учёт остальных CHANGES REQUIRED

- **П.3 (median вместо mean):** `consensus_score[cell] = median(score[m]
  for m in models if score[m][cell] >= 1.0)`. Если voting models < 3 —
  cell не confirmed независимо от median (порог по числу голосов не
  меняется).
- **П.4 (lat/lon в segment):** каждая точка внутри `segments[i].path`
  несёт `{"lat","lon","px_far","px_very_far"}` — те же поля, что уже
  есть у `points`, просто сгруппированы по сегменту с добавлением
  порядка вдоль centerline.
- **П.5 (frontend fallback):** `_buildEuropeOverlaySvgInner` проверяет
  `overlayData.segments && overlayData.segments.length > 0` — при пустом
  массиве (например, все компоненты меньше `MIN_COMPONENT_CELLS`)
  автоматически падает на старый point-by-point рендер, диагностические
  точки не скрываются.
