Принимаю все 5 пунктов. Отдельно — по REQUEST (centerline без NMS/PCA/scipy):

#### Алгоритм: graph-diameter path вместо NMS + PCA

Убираю отдельный шаг NMS полностью — вместо "прорядить сетку, потом
связать" делаю "связать всё как есть, потом извлечь тонкую линию из
готового графа связности". Это снимает риск п.1 (NMS ничего не рвёт,
потому что его больше нет как отдельного шага над сырыми ячейками).

1. **Connected components** — как согласовано, BFS/DFS 8-связность по
   confirmed-ячейкам (`n_valid >= MIN_MODEL_VOTES`), без предварительного
   прореживания. Компонент может быть "толстым" (широкая зона) — это
   нормально на этом шаге.
2. **Отбросить компоненты `size < MIN_COMPONENT_CELLS` (3)** — как
   согласовано.
3. **Centerline = диаметр графа компонента** (стандартный приём "double
   BFS/Dijkstra", без scipy, только `heapq` из стандартной библиотеки):
   - вес ребра между 8-соседями = евклидово расстояние в шагах сетки
     (1.0 для орто-соседей, √2 для диагональных) — чуть точнее, чем
     просто число хопов, на изогнутых линиях с диагональными шагами;
   - шаг A: из произвольной ячейки компонента запустить
     Dijkstra/BFS → найти самую удалённую ячейку `P1`;
   - шаг B: из `P1` запустить Dijkstra/BFS ещё раз → самая удалённая
     ячейка `P2`, с восстановлением пути по parent-указателям;
   - путь `P1 → P2` — это и есть centerline. Это математически гарантированный
     "диаметр" графа компонента (стандартное свойство: для дерева/
     произвольного связного графа с неотрицательными весами два прохода
     BFS/Dijkstra от произвольной точки находят одну из двух самых
     дальних друг от друга точек).
4. **Почему это чинит оба риска из REQUEST:**
   - *"не разрывает прямую линию из соседних ячеек"* — если компонент
     сам по себе есть прямая цепочка соседних ячеек (путь без ветвлений),
     диаметр графа == вся цепочка целиком, ни одна ячейка не теряется.
   - *"корректнее PCA на изгибах"* — путь строится по фактическим рёбрам
     графа (реальная связность ячеек), а не по проекции координат на
     одну ось. На изогнутом фронте (дуга, S-образная кривая) PCA-ось даёт
     одну прямую и путает порядок точек в изгибе; диаметр-путь идёт вдоль
     самой кривой, порядок всегда корректный.
   - *ветвление (T-образная структура)* — диаметр-путь автоматически
     выбирает ГЛАВНУЮ линию (два самых удалённых конца), короткие боковые

Возможно, это осталось от Proposal v1 — в Proposal v2 (предыдущая
запись в этом файле) отдельного шага NMS 3×3 больше нет вообще. Логика

построения графа — поэтому вопрос "разорвёт ли NMS широкую зону" не
возникает: широкая зона остаётся ЦЕЛЫМ компонентом, из неё уже потом
достаётся линия.

итоговой линии/линиях после разбиения на junction'ах, см. П.3) — так
видно, сколько "усечено" при переходе от блоба к линии.

#### П.3 (сегментация + junction-разбиение) — ПРИНЯТО, расширяю v2

Базовый алгоритм (BFS/DFS 8-связность → граф → диаметр графа через
double BFS/Dijkstra) остаётся как в Proposal v2 — PCA/сортировка по оси
там уже не используется, именно поэтому и был предложен граф вместо
неё. Добавляю то, чего не было в v2: **разбиение на junction'ах**.

- После извлечения главного diameter-path (P1→P2) внутри компонента,
  ячейки компонента, НЕ попавшие на этот путь, не отбрасываются, а
  рекурсивно обрабатываются той же процедурой: если среди оставшихся

  снова строится диаметр графа → это отдельный `segments[i]` (боковая
  ветвь), а не потерянные точки.
- Рекурсия останавливается, когда очередной остаток меньше
  `MIN_COMPONENT_CELLS` — эти финальные "хвосты" остаются видны только
  через `points` (fallback), как и раньше.
- Т.е. T-образный фронт даст 2 сегмента (основная линия + боковая ветвь),

Согласен с диагнозом. Проблема концептуальная, не точечный баг: diameter-
path честно находит "диаметр" графа, но применялся он к СЫРОМУ blob'у
(вся широкая confirmed-зона) — а не к уже тонкой линии. Диаметр широкого
прямоугольника — это его противоположные углы, путь между ними идёт по
диагонали через всю область; а "остаток минус путь" на широком blob'е
сам остаётся широким и снова рекурсивно режется на диаметры — отсюда и
"сетка ломаных". Убираю recursive-remainder decomposition полностью,
не патчу — переделываю pipeline, как просили.

#### Новый алгоритм (4 фазы, без recursive-remainder)

**Фаза 1 — Ridge extraction (использует consensus_score_grid напрямую)**

Вместо "взять весь confirmed blob как есть" — сначала утончаем его
через **directional non-maximum suppression по полю consensus_score_grid**
(классическая техника Canny-style NMS, но применяется к ridge непрерывного
скалярного поля, а не к бинарной маске):

1. Считаем `gy, gx = np.gradient(consensus_score_grid)` — направление
   максимального роста score в каждой точке.
2. Для каждой `confirmed`-ячейки `(r,c)`: смотрим на два соседних значения
   score вдоль направления градиента `(gx,gy)/|.|` на расстоянии одного
   шага сетки в обе стороны — **билинейная интерполяция** между соседними
   ячейками grid (не просто ближайший сосед, а честная интерполяция
   вдоль непрерывного направления, чтобы не привязываться к 8 дискретным
   направлениям).
3. Ячейка остаётся `ridge=True`, только если её `score` **строго больше
   или равен** обоих интерполированных соседних значений (локальный
   максимум вдоль направления градиента).
4. Ячейки с `NaN`/невалидным score или вне confirmed в интерполяцию не
   допускаются (маскируются, не тянут ложный максимум с края данных).

Это именно то место, где `consensus_score_grid` **реально участвует** в
выделении оси, а не просто используется постфактум для `avg_score` —
прямое требование review.

**Почему это чинит "12 сегментов из одного blob":** широкий blob по
построению имеет плато/гладкий рост score к центру — directional NMS
по определению оставляет только гребень (1 ячейка в толщину поперёк
направления градиента), а не всю площадь. У ОДНОГО физического фронта
получается ОДНА тонкая линия, а не десяток диаметров вдоль-поперёк.

**Фаза 2 — Compact connectivity (без corner-cut shortcuts)**

Строим граф связности по `ridge`-маске (не по сырому confirmed) со
специальным правилом:

> диагональное ребро `(r,c)–(r+1,c+1)` разрешено, ТОЛЬКО ЕСЛИ хотя бы
> одна из двух "угловых опорных" ячеек `(r,c+1)` или `(r+1,c)` тоже
> входит в `ridge`-маску.

Это стандартное правило анти-алиасинга связности (иначе диагональ
"прорезает" через пустой угол — ровно то, что review просил исключить,
и та же причина, по которой в тесте L-формы диаметр-путь "терял" одну
угловую ячейку в Proposal v3).

**Фаза 3 — Разделение на реально независимые линии**

- Компоненты `ridge`-маски (8-связность с правилом Фазы 2) — это уже
  почти всегда единичные тонкие линии, а НЕ широкие площади, потому что
  утончение произошло на Фазе 1, до связности.
- Внутри компонента считаем степень каждой ячейки (число ridge-соседей
  по разрешённой связности):
  - **`degree <= 2` везде (простая линия или цикл)** → это одна линия
    целиком, без разбиения.
  - **есть узлы `degree >= 3` (реальный junction)** → раскладываем
    компонент на отдельные "рёбра графа" между соседними
    junction/endpoint узлами — стандартная операция "разбить граф на
    максимальные простые пути между вершинами со степенью ≠ 2".
    Сегменты появляются ТОЛЬКО здесь — не из-за произвольного
    "diameter minus remainder", а из-за настоящего ветвления топологии.
  - **отдельный компонент** (не связан 8-связностью с остальными) —
    отдельный сегмент/линия, как и раньше.
- **Recursive "diameter minus remainder → новая линия" полностью
  убирается** — прямое требование review, эта техника была причиной
  проблемы.

**Фаза 4 — Упорядочивание точек внутри уже тонкой линии**

- Простая линия (0 или 2 endpoint, без junction) — обычный обход графа
  от одного конца до другого (граф уже тонкий и почти всегда сам по
  себе путь — здесь диаметр-путь безопасен и даёт тот же результат, что
  и прямой обход, оставляю double-Dijkstra как способ найти "с какого
  конца начать" на случай мелких неровностей толщины в 1-2 ячейки после
  NMS).
- Цикл/петля (`degree == 2` везде, нет endpoint) — редкий крайний
  случай (тест обязателен). Разрезаем цикл в одной точке (два наиболее
  удалённых узла через тот же double-BFS/Dijkstra) и отдаём как одну
  незамкнутую линию, покрывающую весь цикл кроме одного замыкающего
  ребра.
- Junction-ветви (из Фазы 3) — каждая ветвь уже сама по себе простая
  линия между двумя узлами графа, обходится напрямую.

#### 1. Исправленный алгоритм ridge extraction

Вместо направления первой производной беру направление **наибольшей
отрицательной кривизны** (главный собственный вектор Гессиана с меньшим
собственным значением) — это направление "поперёк ridge" и оно НЕ
вырождается на самой вершине ridge (в отличие от градиента).

```
d_row, d_col = np.gradient(score)                  # первые производные (индексное пространство)
H_rr, H_rc_a = np.gradient(d_row)                  # вторые производные
H_cr_b, H_cc = np.gradient(d_col)
H_rc = (H_rc_a + H_cr_b) / 2.0                      # симметризация (две дискретные оценки смешанной производной)

trace = H_rr + H_cc
disc  = np.sqrt(((H_rr - H_cc) / 2.0) ** 2 + H_rc ** 2)
lambda_min = trace / 2.0 - disc                     # наиболее отрицательное собственное значение
lambda_max = trace / 2.0 + disc

# собственный вектор для lambda_min (направление "поперёк ridge"):
#   если H_rc != 0:  v = (H_rc, lambda_min - H_rr), нормировать
#   если H_rc == 0 (матрица уже диагональна): v = ось с МЕНЬШИМ диагональным значением
```

**Ridge-точка, если ОБА условия выполнены:**
1. `lambda_min <= -CURVATURE_EPSILON` — существенная отрицательная
   кривизна хоть в каком-то направлении (это и отличает ridge от
   настоящего плоского участка: у плоского участка `lambda_min ≈ 0`,
   у ridge — заметно отрицательное).
2. Score является локальным максимумом ВДОЛЬ направления `v_min`

**Flat-plateau fallback (лексикографический tie-break из v5) применяется

Направление `v_min` берётся из ВТОРОЙ производной, которая на вершине

#### 3. Eigenvector fallback — надёжная норма, не только `H_rc == 0`

```
v_candidate = (H_rc, lambda_min - H_rr)
norm = sqrt(v_candidate[0]**2 + v_candidate[1]**2)
if norm < VECTOR_EPSILON:
    # матрица численно вырождена в диагональную (или сама norm
    # обнулилась из-за сокращения ошибок округления) —
    # eigenvector для меньшего собственного значения совпадает с осью
    # меньшего диагонального элемента
    v = (1.0, 0.0) if H_rr <= H_cc else (0.0, 1.0)
else:
    v = (v_candidate[0] / norm, v_candidate[1] / norm)
```

`VECTOR_EPSILON` — отдельная малая константа (не путать с
`CURVATURE_EPSILON`), защищает именно от деления на ~0 при нормировке,
а не от неверной кривизны.
