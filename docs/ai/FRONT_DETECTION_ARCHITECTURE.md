# Тема: Архитектура детекции атмосферных фронтов (Satellite → BUFR → Open-Meteo)

_Создано: 2026-09-11, TASK ID: FRONT_DETECTION_ARCHITECTURE_001_

## Исходная цель

Автоматически находить реальные атмосферные фронты (cold, warm, occlusion,
при возможности stationary) и отображать их поверх спутникового снимка, с
типом и confidence. Open-Meteo — обязательный fallback/confirmation layer,
но не единственный и не обязательно основной источник геометрии.

`EUROPE_FRONT_LINE_001` НЕ отменяется и не переделывается в рамках этой
задачи — см. раздел «Связь с EUROPE_FRONT_LINE_001» ниже.

## История проблемы Cloud Mask (со слов пользователя, ~2-4 недели до
2026-09-11, код/коммит не найден)

Была попытка сделать детектор фронтов **по всей Европе** на базе Cloud
Mask (CLM): бинарная сегментация облако/не облако по всему европейскому
охвату. Результат — детектор захватывал **весь (или очень большой) массив
облачности** вместо узкого фронта: континентальная облачность в средних
широтах почти всегда представляет собой обширные связные системы (циклоны,
фронтальные облачные щиты шириной в сотни км), поэтому простой порог
"это облако" / "это не облако" на масштабе всей Европы неизбежно даёт один
гигантский connected component, а не линию.

Код этой попытки не найден в истории коммитов и в `docs/topics/` (архив
`eumetsat_archive.md` покрывает историю с 2026-08-02, но ни разу не
упоминает Europe+CLM; полнотекстовый и commit-search по репозиторию тоже
ничего не дал) — по всей видимости, эксперимент не был закоммичен в
`main` или не был явно задокументирован. Восстановить точную реализацию
невозможно, только симптом (со слов пользователя): "детектор хватал очень
большой (весь) массив облачности вместо предполагаемого фронта". Дальше
в этом документе проблема анализируется по симптому, не по коду.

**Важная структурная параллель.** Ровно та же категория проблемы —
"широкая подтверждённая область вместо узкой линии" — уже была решена в
рамках `EUROPE_FRONT_LINE_001`, но на **модельных** (Open-Meteo grid)
данных, не на спутниковых. Там (см. `AI_DISCUSSION.md`, Proposal v1→v10)
первая версия детектора публиковала все ячейки сетки, прошедшие порог
градиента температуры/давления, независимо друг от друга — визуально
получалась "сетка точек", а не линия. Финальное решение (Proposal v10,
Hessian-based ridge extraction) не отбрасывало часть данных порогом
жёстче, а **утончало** уже подтверждённую широкую область до линии
толщиной в одну ячейку через анализ второй производной (кривизны)
скалярного поля: точка остаётся "ridge", только если кривизна поперёк
предполагаемой линии значимо отрицательна и заметно сильнее кривизны
вдоль линии (anisotropy-критерий, отличающий вытянutый ridge от круглого
изолированного пятна).

**Гипотеза (не проверена на живых данных, для этого нужна Фаза 1
Proposal ниже):** Europe-CLM детектор, скорее всего, повторил раннюю,
уже пройденную ошибку `EUROPE_FRONT_LINE_001` v1 — использовал бинарную
маску "облако/не облако" саму по себе как выход детектора, без этапа
утончения широкой области до узкой линии. У бинарной CLM-маски в принципе
нет непрерывного скалярного поля для анализа кривизны (это 0/1, а не
плотность/температура/градиент) — поэтому даже прямой перенос техники
Hessian ridge extraction с `EUROPE_FRONT_LINE_001` невозможен без
предварительного построения непрерывного поля "фронтальной вероятности"
из спутниковых данных (см. Proposal, Фаза 1).

модельные данные, не спутник).

## Текущие возможности и ограничения существующего (near/west) детектора

Существующий near/west детектор **не имеет** проблемы "хватает весь
массив" — потому что:
1. Область поиска маленькая и локальная (400×400px / west bbox), не вся
   Европа — физически не может встретить континентальный облачный щит
   целиком.
2. Есть явный фильтр `frontlike` — компонент публикуется, только если его
   площадь `>= LARGE_SYSTEM_AREA_KM2` (300 км², "система", не мелкий шум)
   И его `aspect_ratio >= FRONTLIKE_ASPECT_THRESHOLD` (2.2, вытянутая
   форма). Круглые/компактные облачные массивы (обычная конвекция,
   локальная облачность) явно исключаются — `_detect_frontlike_systems()`,
   `eumetsat_west_watch.py`/`eumetsat_cloud_forecast.py`.
3. Есть трекинг во времени (`eumetsat_frontal_track.py`), IR/GC ROI-
   подтверждение (`_west_confirmed()`), привязка к SYNOP-станциям
   (ahead/behind), с 2026-09-07 — классификация тёплый/холодный фронт по
   разнице наблюдений станций.

Ограничения (актуальны, из `docs/topics/eumetsat.md`, обновлено 2026-08-20):
- Precip-канал есть только для near-tier, не для west.
- Не хватает явной дельты температуры/ветра между ahead/behind станциями
  (сейчас только сырые наблюдения по обе стороны).
- Occlusion/stationary типы не классифицируются вообще (только
  тёплый/холодный, и то с 2026-09-07).
- Никакого Europe-wide спутникового охвата нет — это ровно та задача,
  которая привела к проблеме Cloud Mask.
- IR_VETO_SIGMA/aspect-пороги калиброваны по единичным живым случаям
  (2026-08-17/18), не по историческому массиву.

## Связь с EUROPE_FRONT_LINE_001

`EUROPE_FRONT_LINE_001` — отдельная, не отменяемая задача: детекция
фронтальной линии по консенсусу 5 моделей Open-Meteo на европейской

`detect_europe_fronts()`/`extract_europe_segments()`). Статус на
2026-09-11: Proposal v10 реализован (commit `62f224e`, Hessian-based
ridge extraction), ожидает GPT implementation review и визуальной
проверки на живых данных VPS — **не блокируется и не переделывается**
этой задачей.

Роль в новой архитектуре (см. Fusion ниже) — вариант **C** из исходного
задания: `open_meteo_frontal_confirm.py` продолжает работать как
независимый Model Front Detector для всей Европы (как сейчас, statu quo),
и ОТДЕЛЬНО может по запросу выступать как local confirmation detector
вокруг конкретного Satellite Candidate (см. Layer 3 Proposal) — эти два
режима не конфликтуют, используют одну и ту же функцию `detect_europe_fronts`
с разным bbox на входе (сейчас — весь Европа-grid; для confirmation —
маленький bbox вокруг кандидата, что заодно решает предупреждение
задания "не делать большой regular scan, если уже есть локальные
кандидаты").

# Proposal v2: Satellite Front Detector (после GPT review v1)

_v1 → v2: GPT REQUEST CHANGES, 2026-09-11. Полный текст review — см.
`AI_DISCUSSION.md`, запись GPT | TASK FRONT_DETECTION_ARCHITECTURE_001._

## Что изменилось относительно v1

Архитектура (Satellite → BUFR → Open-Meteo), тайловый Europe-wide подход
и 4 уровня confidence — **APPROVED без изменений**, не повторяются здесь.

Отклонено и заменено: центральное предположение v1 "CTH ridge = фронт".
GPT указал верно — CTH ridge может быть линией высоких облаков, частью
облачного щита или другой структурой, никак не гарантированно фронтом.
CTH понижен до статуса **одного из satellite features**, не готового
detector field. Hessian ridge extraction переносится с "готового решения"
на "метод geometry extraction, который нужно ещё обосновать экспериментом
на Фазе 1" — может не подойти, тогда используется boundary extraction
или другой метод (решается по результатам Фазы 1, не заранее).

Также отклонено: прямой `import` внутренних `_ridge_*` из
`open_meteo_frontal_confirm.py` в production-код нового детектора. На
время эксперимента (Фаза 1) — временный импорт для проверки допустим,
вынос в общий `scripts/front_geometry.py` — только после подтверждения,
что метод работает на satellite-поле, не раньше.

Новая центральная схема (вместо "products → CTH ridge → Front"):

```
Satellite products (CLM, CTH, IR105, GeoColour, кадры во времени)
        ↓ feature extraction
Satellite Frontal Probability Field  P_front_satellite(lat, lon)
        ↓ geometry extraction (метод — по результатам Фазы 1)
components → segments → SATELLITE_CANDIDATE
        ↓ BUFR (tangent/normal, станции по обе стороны)
OBS_CONFIRMED / недостаточно → Open-Meteo (локально, bbox кандидата)
        ↓
MODEL_CONFIRMED / OBS_AND_MODEL_CONFIRMED
```

живой случай, на котором калибровался `IR_VETO_SIGMA=-1.0`

### Признаки для сравнения (per GPT review)

1. **CLM geometry**: elongation, orientation, форма компонента, границы
   облачности — уже частично считается в `_detect_frontlike_systems()`
   (`aspect_ratio`, `bbox_km`) — переиспользовать эти функции для
   получения признаков, не переизобретать.
2. **CTH**: градиент, локальный контраст, ridge как ОДИН диагностический
   признак среди прочих (не единственный, не готовое решение — см. выше).
3. **IR105**: градиенты яркостной температуры, протяжённость границ,
   пространственная когерентность.
4. **Temporal**: несколько кадров (буфер, как в `MAX_FRAMES=9` из
   `eumetsat_cloud_forecast.py`), persistence кандидата во времени,
   согласованность движения (уже частично есть в `geocolour_motion.py`/
   `ir_motion.py` — скорость/направление), стабильность ориентации.
5. **GeoColour**: дополнительный диагностический признак, с явной
   оговоркой — учитывать уже задокументированную проблему сумеречной
   контаминации (`docs/topics/eumetsat.md`, "без расчёта угла Солнца") —
   не использовать GC-цвет как источник истины при рассвете/закате без
   явной проверки времени суток.

### Результат Фазы 1

- Набор feature maps по каждому признаку выше, для случаев A и B (или

## PHASE 3 — Geometry Extraction (после Фазы 2)

```
P_front_satellite
        ↓ ridge ИЛИ boundary extraction (метод — по итогам Фазы 1/2)
components → segments → SATELLITE_CANDIDATE
```

Если по итогам эксперимента Hessian ridge extraction (метод из
`open_meteo_frontal_confirm.py`) подтверждается как рабочий на
`P_front_satellite` — используется временный импорт на эксперимент,
вынос в `scripts/front_geometry.py` (ridge extraction, component
extraction, graph ordering, branch handling, geometry validation) —
только после подтверждения, что нужен ОБОИМ детекторам. Если эксперимент
покажет, что лучше подходит boundary extraction или другой метод —
выбирается он, без привязки к уже реализованному коду.

## PHASE 4 — BUFR Confirmation (пересмотрено per REQUIRED CHANGE 6)

Было в v1: просто ближайшие станции к линии кандидата. GPT verdict:
недостаточно — нужно подтверждение по ОБЕ СТОРОНЫ фронта, не просто
близость.

Новая схема, для локального участка сегмента:

```
segment → tangent (направление вдоль сегмента)
        → normal (перпендикуляр)
        → станции по разные стороны normal
             Station A
                 |
                 | ЛИНИЯ ФРОНТА (сегмент)
                 |
             Station B
        → ΔT, ΔPressure, изменение направления/скорости ветра,
          влажность, осадки (если доступны) — поперёк предполагаемой линии
```

Основа для `OBS_CONFIRMED`: не факт близости станции, а именно
**контраст** параметров между station A и station B поперёк сегмента.
Переиспользуется `ground_station_selector.py`/`ground_station_obs_fetch.py`
как источник данных о станциях и наблюдений — но логика выбора station A
vs station B (по стороне normal, не просто ahead/behind вдоль трека, как
сейчас в near/west) — новая, требует правки при реализации (не
затрагивается в этом Proposal, фиксируется как явное требование к
будущей реализации Layer 2).

## PHASE 5 — Open-Meteo Confirmation (без изменений по сути, из v1)

Вызывается локально вокруг кандидата, только если:
- BUFR недостаточно (нет станций по обе стороны в разумном радиусе);
- кандидат над морем;
- станции слишком далеко;
- нужно независимое дополнительное подтверждение сверх BUFR.

`detect_europe_fronts()` вызывается с bbox кандидата + запас, НЕ
полноевропейским bbox — сигнатура функции не меняется.

## Затрагиваемые файлы (Фаза 1, эксперимент — минимум)

- Новый экспериментальный файл (например
  `scripts/experiments/satellite_front_features.py` или аналог, не
  подключается к оркестратору) — читает уже существующие функции
  `field_motion_common.py`/`eumetsat_cloud_forecast.py` для фетча
  тайлов/расчёта CLM-признаков, считает CTH/IR-признаки, сохраняет
  feature maps для визуального разбора.
- Production-файлы (`gh_satellite_pipeline.py`, новый детектор,
  `front_geometry.py`) — НЕ создаются и не трогаются на этой фазе.

## Риски и ограничения (обновлено)

- Главный неразрешённый вопрос — доступность архивных кадров EUMETSAT
  WMS на глубину 3-4 недели для случаев A/B (см. выше) — блокирует
  выбор конкретных тестовых данных, решается первым шагом.

  неопределённость, решается по факту Фазы 1/2, не Proposal-риск для
  устранения сейчас.

  или в редкой сети станций может быть невозможно (в этом случае —
  явный fallback на Open-Meteo, Phase 5).

  учитывается как оговорка признака, не решается в этом Proposal.
