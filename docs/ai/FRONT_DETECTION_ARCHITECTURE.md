# Тема: Архитектура детекции атмосферных фронтов (Satellite → BUFR → Open-Meteo)

_Создано: 2026-09-11, TASK ID: FRONT_DETECTION_ARCHITECTURE_001_

## Исходная цель

Автоматически находить реальные атмосферные фронты (cold, warm, occlusion,
при возможности stationary) и отображать их поверх спутникового снимка, с
типом и confidence. Open-Meteo — обязательный fallback/confirmation layer,
но не единственный и не обязательно основной источник геометрии.

`EUROPE_FRONT_LINE_001` НЕ отменяется и не переделывается в рамках этой
задачи — см. раздел «Связь с EUROPE_FRONT_LINE_001» ниже.

## История проблемы Cloud Mask (со слов пользователя, ~2-4 недели до
2026-09-11, код/коммит не найден)

Была попытка сделать детектор фронтов **по всей Европе** на базе Cloud
Mask (CLM): бинарная сегментация облако/не облако по всему европейскому
охвату. Результат — детектор захватывал **весь (или очень большой) массив
облачности** вместо узкого фронта: континентальная облачность в средних
широтах почти всегда представляет собой обширные связные системы (циклоны,
фронтальные облачные щиты шириной в сотни км), поэтому простой порог
"это облако" / "это не облако" на масштабе всей Европы неизбежно даёт один
гигантский connected component, а не линию.

Код этой попытки не найден в истории коммитов и в `docs/topics/` (архив
`eumetsat_archive.md` покрывает историю с 2026-08-02, но ни разу не
упоминает Europe+CLM; полнотекстовый и commit-search по репозиторию тоже
ничего не дал) — по всей видимости, эксперимент не был закоммичен в
`main` или не был явно задокументирован. Восстановить точную реализацию
невозможно, только симптом (со слов пользователя): "детектор хватал очень
большой (весь) массив облачности вместо предполагаемого фронта". Дальше
в этом документе проблема анализируется по симптому, не по коду.

**Важная структурная параллель.** Ровно та же категория проблемы —
"широкая подтверждённая область вместо узкой линии" — уже была решена в
рамках `EUROPE_FRONT_LINE_001`, но на **модельных** (Open-Meteo grid)
данных, не на спутниковых. Там (см. `AI_DISCUSSION.md`, Proposal v1→v10)
первая версия детектора публиковала все ячейки сетки, прошедшие порог
градиента температуры/давления, независимо друг от друга — визуально
получалась "сетка точек", а не линия. Финальное решение (Proposal v10,
Hessian-based ridge extraction) не отбрасывало часть данных порогом
жёстче, а **утончало** уже подтверждённую широкую область до линии
толщиной в одну ячейку через анализ второй производной (кривизны)
скалярного поля: точка остаётся "ridge", только если кривизна поперёк
предполагаемой линии значимо отрицательна и заметно сильнее кривизны
вдоль линии (anisotropy-критерий, отличающий вытянutый ridge от круглого
изолированного пятна).

**Гипотеза (не проверена на живых данных, для этого нужна Фаза 1
Proposal ниже):** Europe-CLM детектор, скорее всего, повторил раннюю,
уже пройденную ошибку `EUROPE_FRONT_LINE_001` v1 — использовал бинарную
маску "облако/не облако" саму по себе как выход детектора, без этапа
утончения широкой области до узкой линии. У бинарной CLM-маски в принципе
нет непрерывного скалярного поля для анализа кривизны (это 0/1, а не
плотность/температура/градиент) — поэтому даже прямой перенос техники
Hessian ridge extraction с `EUROPE_FRONT_LINE_001` невозможен без
предварительного построения непрерывного поля "фронтальной вероятности"
из спутниковых данных (см. Proposal, Фаза 1).

## Существующие доступные спутниковые продукты (проверено по коду,
2026-09-11)

Источник: EUMETSAT WMS, `https://view.eumetsat.int/geoserver/wms`.

| Слой | Идентификатор | Частота | Использование сейчас |
|---|---|---|---|
| Cloud Mask | `msg_fes:clm` | PT15M | `eumetsat_cloud_forecast.py` (near), `eumetsat_west_watch.py` (west) — бинарная сегментация облако/вода/суша |
| Cloud Top Height | `msg_fes:cth` | ~15 мин (тот же гейт, что CLM) | `eumetsat_cloud_forecast.py` — тренд высоты, ординальный индекс по цвету |
| GeoColour | `mtg_fd:rgb_geocolour` | ~10 мин | `eumetsat_geocolour_motion.py` (near), `eumetsat_west_watch.py` (ROI-подтверждение) |
| ИК 10.5мкм | `mtg_fd:ir105_hrfi` | PT10M | `eumetsat_ir_motion.py` (near), `eumetsat_west_watch.py` (ROI-подтверждение, вето) |
| Осадки | `msg_fes:h60b` | — | `eumetsat_precip_forecast.py`/`precip_motion.py` — **только near-tier**, для west и Европы нет |
| Молния | (см. `eumetsat_lightning_forecast.py`) | — | near-tier only |

**Охват:** near-tier — окно ±2.5° вокруг Одессы (46.44, 30.77), 400×400px,
~0.96-1.39км/px. West-tile — bbox 23.6°-28.6°E (`fc.WEST_BBOX`), ~500км
к СЗ, тот же набор слоёв. **Полноевропейского спутникового тайла сейчас
не существует** — только near+west вокруг Одессы. Полноевропейский охват
сейчас есть только у Open-Meteo grid (`EUROPE_FRONT_LINE_001`,
модельные данные, не спутник).

## Текущие возможности и ограничения существующего (near/west) детектора

Существующий near/west детектор **не имеет** проблемы "хватает весь
массив" — потому что:
1. Область поиска маленькая и локальная (400×400px / west bbox), не вся
   Европа — физически не может встретить континентальный облачный щит
   целиком.
2. Есть явный фильтр `frontlike` — компонент публикуется, только если его
   площадь `>= LARGE_SYSTEM_AREA_KM2` (300 км², "система", не мелкий шум)
   И его `aspect_ratio >= FRONTLIKE_ASPECT_THRESHOLD` (2.2, вытянутая
   форма). Круглые/компактные облачные массивы (обычная конвекция,
   локальная облачность) явно исключаются — `_detect_frontlike_systems()`,
   `eumetsat_west_watch.py`/`eumetsat_cloud_forecast.py`.
3. Есть трекинг во времени (`eumetsat_frontal_track.py`), IR/GC ROI-
   подтверждение (`_west_confirmed()`), привязка к SYNOP-станциям
   (ahead/behind), с 2026-09-07 — классификация тёплый/холодный фронт по
   разнице наблюдений станций.

Ограничения (актуальны, из `docs/topics/eumetsat.md`, обновлено 2026-08-20):
- Precip-канал есть только для near-tier, не для west.
- Не хватает явной дельты температуры/ветра между ahead/behind станциями
  (сейчас только сырые наблюдения по обе стороны).
- Occlusion/stationary типы не классифицируются вообще (только
  тёплый/холодный, и то с 2026-09-07).
- Никакого Europe-wide спутникового охвата нет — это ровно та задача,
  которая привела к проблеме Cloud Mask.
- IR_VETO_SIGMA/aspect-пороги калиброваны по единичным живым случаям
  (2026-08-17/18), не по историческому массиву.

## Связь с EUROPE_FRONT_LINE_001

`EUROPE_FRONT_LINE_001` — отдельная, не отменяемая задача: детекция
фронтальной линии по консенсусу 5 моделей Open-Meteo на европейской
сетке ~220км (`scripts/open_meteo_frontal_confirm.py`,
`detect_europe_fronts()`/`extract_europe_segments()`). Статус на
2026-09-11: Proposal v10 реализован (commit `62f224e`, Hessian-based
ridge extraction), ожидает GPT implementation review и визуальной
проверки на живых данных VPS — **не блокируется и не переделывается**
этой задачей.

Роль в новой архитектуре (см. Fusion ниже) — вариант **C** из исходного
задания: `open_meteo_frontal_confirm.py` продолжает работать как
независимый Model Front Detector для всей Европы (как сейчас, statu quo),
и ОТДЕЛЬНО может по запросу выступать как local confirmation detector
вокруг конкретного Satellite Candidate (см. Layer 3 Proposal) — эти два
режима не конфликтуют, используют одну и ту же функцию `detect_europe_fronts`
с разным bbox на входе (сейчас — весь Европа-grid; для confirmation —
маленький bbox вокруг кандидата, что заодно решает предупреждение
задания "не делать большой regular scan, если уже есть локальные
кандидаты").

# Proposal: Satellite Front Detector (Layer 1), минимально инвазивный

Код не менять до APPROVE (GPT review) — см. `AI_DISCUSSION.md`.

## 1. Входные спутниковые продукты

Продолжение уже проверенного набора near/west-детектора, БЕЗ добавления
новых слоёв на первой версии:
- `msg_fes:clm` (Cloud Mask) — основа сегментации, как сейчас.
- `msg_fes:cth` (Cloud Top Height) — источник непрерывного скалярного
  поля для ridge extraction (см. п.3) — в отличие от бинарной CLM, CTH
  уже даёт непрерывную величину, у которой физически осмысленно искать
  кривизну/градиент. Уже выкачивается в `eumetsat_cloud_forecast.py`,
  просто не использовался для геометрии линии, только для тренда высоты.
- ИК/GeoColour — как сейчас, ТОЛЬКО для ROI-подтверждения кандидата
  (`_west_confirmed()`-подобная логика), не для самой геометрии.

## 2. Один кадр или последовательность

Один кадр для геометрии кандидата (как сейчас в `_detect_frontlike_systems`),
последовательность (буфер, как в `eumetsat_cloud_forecast.py`,
`MAX_FRAMES=9`) — только для скорости/направления движения уже
найденного кандидата, без изменений от текущей схемы трекинга
(`eumetsat_frontal_track.py`).

## 3. Алгоритм поиска кандидатов (ключевое отличие от Europe-CLM
неудачи)

Два раздельных масштаба, НЕ один общеевропейский проход:

**(a) Near/west (Одесса-центрированный, уже работает)** — без изменений:
`_detect_frontlike_systems()` на CLM-маске с фильтром
area+aspect_ratio, как сейчас.

**(b) Europe-wide satellite candidate search (новое, отсутствовало)** —
применяется тайловый обход (как near/west, только систематически по
сетке тайлов, покрывающей Европу — переиспользуется геометрия тайлов,
уже принятая для `WEST_BBOX`, просто размноженная на N тайлов вместо
одного) СО следующим изменением относительно неудачной попытки:

1. На каждом тайле строится не бинарная CLM-маска сама по себе, а
   непрерывное поле **CTH внутри облачной области** (`CTH, где CLM==cloud;
   NaN иначе` — тот же приём маскирования, что уже есть в
   `eumetsat_cloud_forecast.py` для тренда высоты, просто применяется
   по всей площади тайла, а не только в `LOCAL_RADIUS_KM` вокруг
   Одессы).
2. К этому полю применяется **тот же Hessian-based ridge extraction**,
   что уже реализован и протестирован в `open_meteo_frontal_confirm.py`
   (`_ridge_mask`, `_valid_ridge_neighbors`, `_ridge_components`,
   `_classify_and_order_component`, константы `CURVATURE_EPSILON`/
   `RIDGE_ANISOTROPY_RATIO`/`MIN_ELONGATION_RATIO`) — переиспользуется
   как библиотека, не переписывается заново. Физический смысл: фронт —
   это не "облако против не-облака", а **гребень высоты облачности**
   (вдоль линии фронта облака выше/плотнее, чем по обе стороны от неё) —
   это именно то непрерывное поле, для которого ridge extraction
   математически осмыслен, в отличие от бинарной маски.
3. Результат — тонкие линии-кандидаты (`SATELLITE_CANDIDATE`) вместо
   одного гигантского connected component, по построению (та же причина,
   по которой это сработало для `EUROPE_FRONT_LINE_001`).

Явное ограничение первой версии: возможна лишняя фрагментация одного
физического фронта на несколько соседних тайлов (граница тайлов) —
переиспользуется уже существующий приём `_merge_near_west()`
(объединение кандидатов у границы тайлов по расстоянию), обобщённый на
N тайлов вместо двух.

## 4. Геометрия кандидата

Полилиния (упорядоченный список точек ridge-пути), как уже отдаёт
`extract_europe_segments()` для модельных данных — те же поля
`{lat, lon, px_...}` на точку, `avg_score`/`n_cells` на сегмент. Формат
согласован с уже существующим `europe_frontal_overlay.json`, чтобы
фронтенд-код (`_buildEuropeOverlaySvgInner`) потенциально мог рисовать
оба источника одним и тем же рендер-путём (не гарантируется в этом
Proposal, но явно не исключается — минимальная инвазивность).

## 5. Данные BUFR для подтверждения

Вокруг каждой точки кандидата (или упрощённо — вокруг двух-трёх
опорных точек сегмента, не каждой точки полилинии, чтобы не разрастись
в N BUFR-запросов на кандидат) ищутся ближайшие станции через уже
существующий `ground_station_selector.py`/`ground_station_obs_fetch.py`
(SYNOP/BUFR), как уже делается для near/west (`ahead_station`/
`behind_station`). Признаки: температурный контраст, скачок давления,
разворот/усиление ветра, влажность, осадки — те же поля, что уже
приходят из `ground_station_obs_fetch.py`, не вводится новый набор
параметров.

## 6. Когда вызывается Open-Meteo

Только если BUFR недостаточно: кандидат над морем (нет станций в радиусе
поиска), либо расстояние до ближайшей станции больше порога (использовать
уже существующую логику "недостаточно данных" из `ground_station_selector.py`,
если она там есть — иначе завести явный `MAX_STATION_DIST_KM`, деталь
уточняется при реализации), либо нужно дополнительное независимое
подтверждение сверх BUFR.

## 7. Локализация запроса Open-Meteo

`detect_europe_fronts()` вызывается с **маленьким bbox вокруг конкретного
кандидата** (например, bbox сегмента + запас в 1-2 ячейки сетки) вместо
текущего полноевропейского bbox — прямое требование задания ("не
выполнять большой regular scan, если уже есть локальные кандидаты").
Функция уже принимает bbox параметром (используется и для far, и для
very_far тайлов сейчас) — переиспользуется без изменения сигнатуры.

## 8. JSON schema результата (черновая, уточняется после анализа
существующего pipeline — прямое требование задания)

```json
{
  "front_id": "...",
  "type": "cold | warm | occlusion | stationary | unknown",
  "confidence_source": "SATELLITE_CANDIDATE | OBS_CONFIRMED | MODEL_CONFIRMED | OBS_AND_MODEL_CONFIRMED",
  "geometry": {"path": [{"lat":..., "lon":...}]},
  "satellite": {"tile_ids": [...], "avg_cth_contrast": ...},
  "bufr_confirmation": {"available": bool, "ahead_station":..., "behind_station":..., "temp_diff":..., "pressure_diff":...},
  "model_confirmation": {"available": bool, "bbox":..., "n_models_confirmed":...},
  "last_seen": "...", "track_id": ...
}
```

## 10. Риски и ограничения

- **Гипотеза о причине Europe-CLM неудачи не проверена на реальных
  данных** (код не найден) — Фаза 1 реализации должна начаться с
  небольшого теста на 1-2 живых тайлах, до полного европейского обхода,
  чтобы подтвердить/опровергнуть гипотезу "нужен continuous field, не
  binary mask" на практике.
- CTH — ординальный индекс по цвету легенды, не метры (уже
  задокументированное ограничение) — ridge extraction по нему даёт
  относительную, не абсолютную геометрию.
- Тайловый обход всей Европы — сетевая нагрузка (N тайлов × несколько
  слоёв) кратно больше, чем текущий near+west — нужна оценка частоты
  обновления (вряд ли раз в 15 мин, как near-tier).
- Стыковка кандидатов на границах тайлов — известное упрощение
  (`_merge_near_west`-подобный приём), может давать разрывы.
- Occlusion/stationary классификация — не покрывается этим Proposal,
  только структура `type` в JSON зарезervирована под них.
- Никакой код не написан и не запущен — это Proposal, ожидает GPT review
  (см. `AI_DISCUSSION.md`, TASK FRONT_DETECTION_ARCHITECTURE_001) перед
  реализацией.
