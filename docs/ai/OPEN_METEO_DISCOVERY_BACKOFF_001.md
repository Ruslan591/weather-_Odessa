## Root cause analysis

### 1. Почему `fetch_run_time_and_interval()` дёргает meta.json каждые 5 мин для
модели, чей run не менялся

Не баг — осознанный дизайн (`vps_pipeline.py`, докстринг у
`STALE_BACKOFF_MULTIPLIER`). Расписание имеет только ДВА состояния:
- `now < next_expected` → 0 запросов (due-gate закрыт);
- `is_same_run=True` и `overdue ≤ 3×update_interval` → due=True на КАЖДОМ
  cron-тике (5 мин), без прогрессии;
- `overdue > 3×update_interval` → backoff, next_expected = now + 6ч.

`next_expected = last_run + 0.7×update_interval` (margin
`SCHEDULE_MARGIN_FRACTION=0.30`, чтобы не проспать ранний прогон).
Промежуточное состояние "уже пора, но реального прогона ещё нет" (типичная
задержка публикации ECMWF/UKMO на 1-3ч сверх номинала) может длиться ЧАСЫ,
и всё это время модель проверяется раз в 5 минут без исключения.

### 2. Текущая механика last_run / update_interval / next_expected / due-gate

`due` — чисто локальная проверка (без сети) `now >= next_expected`. Только
при `due=True` идёт один HTTP GET на `meta.json`. По ответу:
- если `run_time` совпал с `last_run` (допуск 30 мин, из-за балансировщика
  Open-Meteo) → `is_same_run=True`, `next_expected` пересчитывается ОТ
  `last_run` (не от старого `next_expected` — так дрейф исключён
  структурно), либо ставится backoff +6ч, если просрочка > 3×interval;
- если run новый → history обновляется, `next_expected` считается от
  нового `run_time`.

### 3. Почему нет прогрессивного backoff для здоровой, но запаздывающей модели

Архитектура содержит только два порога: 5 мин (не stale) и 6ч (объявили
stale). Промежуточной прогрессии (5→10→20→40 мин) нет вообще — это и есть
основной источник лишнего трафика.

### 4. Оценка объёма discovery-полинга

По паспортным интервалам из кода (ICON EU — 3ч/10800с, остальные 7 моделей
— 6ч/21600с) и типичной задержке публикации 1-3ч сверх номинала:
- 6ч-модели (ECMWF, UKMO, ARPEGE World, GFS, GEM, GRAPES): ~18 запросов на
  прогон × 4 прогона/сутки × 6 моделей ≈ **~430 запросов/сутки**;
- 3ч-модели (ICON EU, ICON Global): ~18 запросов × 8 прогонов/сутки × 2
  модели ≈ **~290 запросов/сутки**;
- Итого фоновый discovery-трафик **≈ 700-800 запросов/сутки** —
  независимо от того, менялся ли когда-либо форекаст-код.

(Оценка приблизительная — точные цифры нужно снять из реального
`_open_meteo_requests.jsonl` за сутки, задача на верификацию ниже.)

### 5. Сочетание с burst `open_meteo_frontal_confirm.py`

Сам burst (5 моделей, пауза `REQUEST_INTERVAL=30с`) живьём проверен как
безопасный отдельно (300 точек×7 полей×5 моделей — все 200 OK,
2026-09-06). Тайминг сегодняшнего инцидента (07:42:12→07:43:47, шаг
~30-35с) совпадает с нормальной работой скрипта — аномалии в его СОБСТВЕННОМ
поведении нет. При этом:
- `vps_satellite_pipeline.py` запускает `check_open_meteo_frontal_confirm()`

- `vps_pipeline.py` discovery (due-check по 8 моделям) идёт на своём

  НЕТ — есть только пост-фактум circuit breaker (`open_meteo_guard.py`),

- Прецедент: `open_meteo_field_fetch.py` + `open_meteo_very_far_line.py`

### 6. Burst — непосредственная причина или последний в очереди

Скорее последний в очереди. Собственная нагрузка `frontal_confirm.py`
типовая и ранее подтверждена безопасной; упал 4-й запрос из 5 (UKMO), а
не первый — значит порог был пройден СОВОКУПНЫМ трафиком (discovery
`vps_pipeline.py` + возможные параллельные вызовы `vps_satellite_pipeline.py`)
в тот же интервал времени, а не самим burst'ом.

Второй эпизод (08:15:09, `update.py`→forecast) подтверждает системность:
probe-owner circuit breaker'а — дешёвый `meta.json` (ecmwf_ifs), а НЕ
тяжёлый `/v1/forecast`. Успешный probe мгновенно переводит guard
OPEN→CLOSED и разом "отпускает" ВСЕ модели/скрипты, чьи due-статусы
копились за 30 минут cooldown (см. докстринг про "скачок" в
`OPEN_METEO_REQUEST_ARCHITECTURE.md`). Получается thundering herd сразу
после восстановления — тяжёлый forecast-запрос ловит 429 повторно почти
сразу же, хотя формальный cooldown уже истёк.

## Proposal

1. **Общий rate-limiter вместо только реактивного circuit breaker.**
   Персистентный sliding-window/token-bucket файл
   (`data/_open_meteo_rate_window.json`), через который проходят ВСЕ
   точки входа (meta, forecast, historical, batch) перед любым запросом —
   не только после факта 429.
2. **Плавное открытие после cooldown вместо разового "шлюза".** После
   успешного probe — не открывать все due-очереди разом, а выпускать по
   1 запросу с паузой (напр. `REQUEST_INTERVAL=30с`) до исчерпания
   накопившейся due-очереди.
3. **Прогрессивный backoff между 5 мин и 6ч.** Счётчик подряд неудачных
   due-check одной модели → интервал растёт 5→10→20→40 мин (потолок
   ~1ч), сброс к 5 мин при обнаружении нового run. Не меняет семантику
   `is_same_run`/`stale`, только частоту опроса в промежуточном состоянии.
4. **Развести probe-эндпоинт с реально проблемным классом запросов.** Если
   тяжёлые forecast-запросы продолжат падать сразу после успешного
   meta-probe — завести отдельный "тяжёлый" probe для forecast-класса,
   независимый от дешёвого meta-probe.
