## Root cause analysis

### 1. Почему `fetch_run_time_and_interval()` дёргает meta.json каждые 5 мин для
модели, чей run не менялся

Не баг — осознанный дизайн (`vps_pipeline.py`, докстринг у
`STALE_BACKOFF_MULTIPLIER`). Расписание имеет только ДВА состояния:
- `now < next_expected` → 0 запросов (due-gate закрыт);
- `is_same_run=True` и `overdue ≤ 3×update_interval` → due=True на КАЖДОМ
  cron-тике (5 мин), без прогрессии;
- `overdue > 3×update_interval` → backoff, next_expected = now + 6ч.

`next_expected = last_run + 0.7×update_interval` (margin
`SCHEDULE_MARGIN_FRACTION=0.30`, чтобы не проспать ранний прогон).
Промежуточное состояние "уже пора, но реального прогона ещё нет" (типичная
задержка публикации ECMWF/UKMO на 1-3ч сверх номинала) может длиться ЧАСЫ,
и всё это время модель проверяется раз в 5 минут без исключения.

### 2. Текущая механика last_run / update_interval / next_expected / due-gate

`due` — чисто локальная проверка (без сети) `now >= next_expected`. Только
при `due=True` идёт один HTTP GET на `meta.json`. По ответу:
- если `run_time` совпал с `last_run` (допуск 30 мин, из-за балансировщика
  Open-Meteo) → `is_same_run=True`, `next_expected` пересчитывается ОТ
  `last_run` (не от старого `next_expected` — так дрейф исключён
  структурно), либо ставится backoff +6ч, если просрочка > 3×interval;
- если run новый → history обновляется, `next_expected` считается от
  нового `run_time`.

### 3. Почему нет прогрессивного backoff для здоровой, но запаздывающей модели

Архитектура содержит только два порога: 5 мин (не stale) и 6ч (объявили
stale). Промежуточной прогрессии (5→10→20→40 мин) нет вообще — это и есть
основной источник лишнего трафика.

### 4. Оценка объёма discovery-полинга

По паспортным интервалам из кода (ICON EU — 3ч/10800с, остальные 7 моделей
— 6ч/21600с) и типичной задержке публикации 1-3ч сверх номинала:
- 6ч-модели (ECMWF, UKMO, ARPEGE World, GFS, GEM, GRAPES): ~18 запросов на

- 3ч-модели (ICON EU, ICON Global): ~18 запросов × 8 прогонов/сутки × 2
  модели ≈ **~290 запросов/сутки**;
- Итого фоновый discovery-трафик **≈ 700-800 запросов/сутки** —

### 6. Burst — непосредственная причина или последний в очереди

[УТОЧНЕНО по замечанию GPT v1→v2] Формулировка "скорее последний в очереди"
из v1 — это ВЕРОЯТНАЯ гипотеза, а не доказанный факт: реального совместного
лога всех 5 точек входа Open-Meteo за 07:40-07:44 с точностью до секунды
нет, поэтому "совокупный трафик от параллельных cron-процессов" — правдоподобная,
но не подтверждённая напрямую причина. Собственная нагрузка `frontal_confirm.py`
типовая и ранее подтверждена безопасной; упал 4-й запрос из 5 (UKMO), а
не первый — это согласуется с гипотезой "burst как последний в очереди",
но не исключает других версий (напр. непредсказуемого transient-лимита на
стороне Open-Meteo). Burst считаем вероятным фактором/последним запросом
очереди, НЕ доказанной первопричиной 429 — до появления точных данных из
`_open_meteo_requests.jsonl` по всем скриптам за этот интервал.

Второй эпизод (08:15:09, `update.py`→forecast) подтверждает системность:
probe-owner circuit breaker'а — дешёвый `meta.json` (ecmwf_ifs), а НЕ
тяжёлый `/v1/forecast`. Успешный probe мгновенно переводит guard
OPEN→CLOSED и разом "отпускает" ВСЕ модели/скрипты, чьи due-статусы
копились за 30 минут cooldown (см. докстринг про "скачок" в
`OPEN_METEO_REQUEST_ARCHITECTURE.md`). Получается thundering herd сразу
после восстановления — тяжёлый forecast-запрос ловит 429 повторно почти
сразу же, хотя формальный cooldown уже истёк.

## Proposal (v2, с учётом 4 уточнений GPT)

1. **Прогрессивный backoff между 5 мин и 6ч.** [УТОЧНЕНО: явная шкала]
   Счётчик подряд неудачных due-check одной модели (`is_same_run=True`,
   ещё не stale) → интервал следующей проверки растёт по шкале
   **5 → 10 → 20 → 40 → 60 мин** (потолок 60 мин, не 40), сброс к 5 мин
   немедленно при обнаружении нового run (`is_same_run=False`). После
   потолка 60 мин интервал не растёт дальше — до срабатывания отдельного
   stale-порога (`overdue > 3×interval` → 6ч backoff, как сейчас, не
   меняется). Не трогает семантику `is_same_run`/`STALE_BACKOFF_MULTIPLIER`.

2. **Общий rate-limiter — конкретная схема и параметры (v3, зафиксировано).**
   [УТОЧНЕНО: алгоритм и числа больше не открыты]

   - **Алгоритм**: token bucket + жёсткий минимальный интервал (два
     независимых условия, оба должны выполниться для разрешения).
   - **Ёмкость/refill**: capacity = **8 токенов**, refill = **1 токен
     каждые 8 секунд** (устойчивый темп ≈7,5 запроса/мин, ≈450/час —
     заведомо ниже документированных 600/мин и 5000/час; ёмкость 8
     покрывает легитимный burst — напр. backfill по 8 моделям в
     `fetch_historical_model`-цикле update.py).
   - **Минимальный интервал**: `MIN_INTERVAL_SEC = 3` — ни один реальный
     forecast/archive-запрос не может быть разрешён раньше чем через 3с
     после ПРЕДЫДУЩЕГО разрешённого (глобально, межпроцессно), даже если
     токены есть. Это отдельная защита именно от одновременного старта
     запросов из независимых cron-процессов (`vps_pipeline.py` +
     `vps_satellite_pipeline.py` + `update.py`), которую чистый
     token-bucket сам по себе не гарантирует (токены могут закрыть
     несколько параллельных reserve() почти одновременно).
   - **Область действия**: бюджет считается ТОЛЬКО по `/v1/forecast` и
     `/v1/archive`. Запросы к `/data/{metaId}/static/meta.json`
     (discovery, due-check) в этот бюджет НЕ входят — у них своя частота
     через backoff-шкалу п.1, без token-bucket. Обоснование: meta.json —
     статический файл с иной (не API-квотной) моделью ограничений на
     стороне Open-Meteo, чем и объяснялось несовпадение поведения
     дешёвого probe и реального повторного 429 на forecast в 08:15:09.
   - **Хранение**: `data/_open_meteo_rate_window.json` (`tokens`,
     `last_refill_at`, `last_granted_at`), лок — отдельный
     `data/_open_meteo_rate_window.lock` (тот же flock-паттерн, что и у
     `_open_meteo_cooldown.lock`).
   - **Что происходит при отсутствии разрешения**: `reserve()` атомарно
     возвращает `"denied"` СРАЗУ (без ожидания/retry внутри лока — под
     flock не спим). Вызывающий скрипт трактует `"denied"` ТОЧНО как
     нынешний `gate()=="skip"`: пропускает именно эту модель/дату в этом
     цикле, следующая попытка — на следующем естественном триггере
     (следующий due-тик, следующая итерация backfill-цикла). Никакой
     очереди/busy-wait внутри лока не создаётся.
   - Лимитер и circuit breaker (`OPEN`/`RECOVERING`/`CLOSED`, п.3)
     — НЕЗАВИСИМЫЕ проверки. Реальный HTTP-запрос идёт, только если ОБЕ
     разрешили: guard в состоянии, допускающем запрос (`proceed` или
     выданный `RECOVERING`-слот), И limiter выдал токен/интервал прошёл.

3. **RECOVERING-состояние вместо разового "OPEN→CLOSED" шлюза (v3, N зафиксировано).**
   [УТОЧНЕНО: третье состояние guard'а, точные критерии]
   `open_meteo_guard.py` получает состояние `RECOVERING` между `OPEN` и
   `CLOSED`:
   - после успешного probe (дешёвый meta.json-запрос по ecmwf_ifs) guard
     переходит не сразу в `CLOSED`, а в `RECOVERING`, счётчик
     `recovering_streak = 0`;
   - в `RECOVERING` каждый следующий forecast/archive-вызов (ЛЮБОЙ из
     точек входа, не только probe-owner) получает разрешение
     ПОСЛЕДОВАТЕЛЬНО, не раньше чем через `RECOVERY_INTERVAL ≥ 30с`
     после предыдущего РАЗРЕШЁННОГО запроса — due-очередь, накопившаяся
     за cooldown, разбирается по одному, не разом. Каждый такой запрос
     ТАКЖЕ обязан пройти общий межпроцессный atomic limiter из п.2
     (двойная проверка: RECOVERING-таймер И token-bucket/min-interval);
   - **N = 3** зафиксировано: переход `RECOVERING → CLOSED` — после ровно
     3 подряд успешных реальных forecast/archive-запросов;
     `recovering_streak` сбрасывается в 0 при входе в `RECOVERING`;
   - **Классификация исхода каждого recovery-запроса**:
     — `2xx` → success, `recovering_streak += 1`; при достижении 3 —
       `state = CLOSED`, `trips = 0`, `cooldown_until = None`;
     — `429` → НЕМЕДЛЕННО `state = OPEN` (см. п. "Backoff — точная
       механика" ниже про рост cooldown), `recovering_streak` не имеет
       значения (state уже не RECOVERING);
     — любая другая ошибка (не-2xx HTTP, timeout, network error) → это
       НЕ success: `recovering_streak` НЕ увеличивается, но и НЕ
       сбрасывается в 0, `state` остаётся `RECOVERING` (это НЕ признак
       throttling на стороне Open-Meteo, а обычная сетевая помеха —
       трактовать её как повод откатиться в `OPEN` было бы избыточно
       строго). Если это допущение нежелательно — просьба к GPT явно
       указать, что в этом случае `recovering_streak` тоже нужно
       сбрасывать в 0.
   - Если pending due-запросов (due-check по любой модели ИЛИ
     запланированный forecast-фетч) в момент нахождения в `RECOVERING`
     нет — `RECOVERING` НЕ создаёт синтетических/дополнительных
     запросов сам по себе. Он только регулирует темп ВЫДАЧИ разрешений
     для запросов, которые и так должны были случиться по due-gate/diff
     логике. Если реальных due-запросов долго нет, `RECOVERING` может
     оставаться активным неопределённо долго до первого реального
     forecast/archive-вызова — это осознанно, отдельного таймаута на
     сам факт нахождения в `RECOVERING` не вводится.

### Backoff guard — точная механика (проверено по факту кода `open_meteo_guard.py` 2026-09-13)

**Текущая реализация (ДО изменений, дословно по коду):**
- `_BACKOFF_SECONDS = {1: 1800, 2: 3600}`, `_BACKOFF_CEILING = 7200`.
- `record_429()` (вызывают НЕ-probe точки входа): если `state == CLOSED`
  → переход в `OPEN`, `trips = 1`, `cooldown_until = now + 1800` (30 мин).
  Если `state` уже `OPEN` — **чистый no-op**: ни `trips`, ни
  `cooldown_until` НЕ меняются. То есть рост 1ч/2ч НЕ происходит от
  повторных 429 обычных (не-probe) вызовов — только от провалов
  РЕКАВЕРИ-ПОПЫТКИ, ниже.
- `report_probe_result(success)` (вызывает ТОЛЬКО probe-owner,
  ecmwf_ifs-проверка в `vps_pipeline.py`, ПОСЛЕ истечения `cooldown_until`):
  при `success=True` → `state=CLOSED`, `trips=0`, `cooldown_until=None`.
  При `success=False` → `trips += 1`, `cooldown_until = now +
  _BACKOFF_SECONDS.get(trips, _BACKOFF_CEILING)` → для trips=1→1800с(30м),
  trips=2→3600с(1ч), trips≥3→7200с(2ч, потолок, дальше не растёт).
- **Итог по факту кода**: рост 30м→1ч→2ч — это рост от ПОСЛЕДОВАТЕЛЬНЫХ
  ПРОВАЛОВ САМОГО PROBE (дешёвый meta.json ecmwf_ifs) после истечения
  cooldown, а НЕ от повторных 429 на тяжёлых forecast/archive-запросах
  из других точек входа (которые сейчас идут ПОСЛЕ probe и вообще не
  учитываются в `trips`, если probe уже отчитался как `success`).
  Именно этот разрыв (probe meta успешен → но реальный forecast сразу
  падает 429, как в 08:15:09) и закрывает п.3/RECOVERING выше.

**Новая механика (v3, что именно будет реализовано):**
- Единый счётчик `trips`, растущий по ТОЙ ЖЕ таблице
  `{1: 1800, 2: 3600, default: 7200}`, но теперь инкрементируется в ДВУХ
  случаях (а не только при провале probe):
  1. Провал probe (meta.json ecmwf_ifs) после истечения cooldown — как
     сейчас, без изменений.
  2. Реальный `429` на forecast/archive-запросе ВО ВРЕМЯ `RECOVERING`
     (см. п.3) — засчитывается как провал рекавери-попытки, `trips += 1`
     по той же таблице, `state = OPEN`.
- `trips` сбрасывается в `0` ТОЛЬКО при полном успехе рекавери — 3 подряд
  успешных forecast/archive-запроса в `RECOVERING` (`state → CLOSED`).
  Успешный ОДИН probe (переход `OPEN → RECOVERING`) `trips` НЕ сбрасывает
  — рекаверия ещё не подтверждена.
- `record_429()` от НЕ-probe вызовов, когда `state` уже `OPEN` — остаётся
  no-op, как сейчас (хвостовые запросы, стартовавшие до закрытия ворот,
  по-прежнему не влияют на backoff).
- Потолок `_BACKOFF_CEILING = 7200` (2ч) не меняется.

4. **Limiter — межпроцессный, атомарный, на уровне КАЖДОГО запроса.**
   [УТОЧНЕНО: не batch-level] Каждый реальный HTTP-запрос к
   `/v1/forecast`/`/v1/archive` (не meta.json — см. п.2) проходит
   отдельную атомарную проверку НЕПОСРЕДСТВЕННО перед собой, по схеме:
   `flock(lock-файл) → read(state) → decide(budget/RECOVERING-таймер) →
   reserve(бюджет/таймстамп) → save(state) → unlock`. Это меняет текущий
   паттерн вызова: сейчас `gate()` вызывается ОДИН раз перед циклом по
   нескольким моделям (`update.py`, `open_meteo_frontal_confirm.py`) — в
   v2 гейт проверяется на КАЖДОЙ итерации цикла, перед каждым отдельным
   forecast-запросом, а не один раз на весь batch. Реализация — тот же
   flock-паттерн, что уже используется в `open_meteo_guard.py` и
   `vps-github-bridge` для git-операций.
