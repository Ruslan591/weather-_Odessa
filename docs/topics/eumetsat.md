# Тема: Спутниковый пайплайн EUMETSAT

_Последнее обновление: 2026-08-02 (фикс радиуса station_state в GeoColour)_

## Что это
Спутниковый модуль проекта верификации погоды Одессы: карты и анализ облачности на базе EUMETSAT WMS.

## Файлы
- `eumetsat.html` — интерактивная карта Leaflet с анимированными WMS-слоями EUMETSAT
- `eumetsat.js` — логика карты; охват (`ANIM_BOUNDS`) больше НЕ хардкод, читается из `data/anim/manifest.json` (`_bounds`)
- `nearby.html` / `nearby_precip.js` — карточный анализ облачного движения/прогноза, только EUMETSAT (PWS-сенсоры и RainViewer удалены из этого блока)
- `scripts/eumetsat_cloud_forecast.py` — бэкенд-расчёт блока "Облачность": classification (clear/variable/cloud), движение, тренды density/height/shape
- `scripts/eumetsat_anim_render.py` — рендер MP4-петель для `eumetsat.html` (широкий обзорный охват, ЕДИНАЯ точка конфигурации — `BBOX`, см. ниже)
- `scripts/field_motion_common.py` — общие константы проекции узкого окна анализа (CENTER_LAT/LON, HALF_WINDOW_DEG=2.5°, TILE_SIZE=400, KM_PER_PX и т.д.), используется несколькими eumetsat_*_motion.py и eumetsat_cloud_forecast.py скриптами

## Технические детали (проверено, работает)
- Endpoint: `https://view.eumetsat.int/geoserver/wms`
- CRS: `CRS:84` (НЕ EPSG:3857), bbox в порядке `lon,lat`
- Центр тайла: Одесса (46.4406, 30.7703), окно ±2.5° (HALF_WINDOW_DEG), 400×400px
- Масштаб: ~0.96 км/px по X, ~1.39 км/px по Y
- Рабочие слои: `msg_fes:clm`, `msg_fes:cth`, `msg_fes:h60b`, `msg_fes:gii_kindex`, `msg_fes:ir108`, `msg_fes:ir039`, `mtg_fd:li_afa`, `mtg_fd:rgb_geocolour`, `mtg_fd:ir105_hrfi`
- Частота слоёв: `msg_fes:*` — 15 мин; `mtg_fd:li_afa` — 5 мин; `mtg_fd:rgb_geocolour` — 10 мин
- `time=None` (latest) часто отдаёт дубль последнего явного тайм-стампа (publication lag)
- `mtg_fd:*` слои без nearestValue-снэппинга → `build_time_steps()` выравнивает по границам шага
- GetLegendGraphic для mosaic-слоёв → XML-ошибка → используются статические HTML-легенды
- CLM классификация: nearest-color к 3 анкерам — `clear_water`(0,0,255), `clear_land`(0,170,0), `cloud`(255,255,255)

## 2026-08-02: закрыт вопрос MTG CLM/CTTH
Проверили `GetCapabilities` (список слоёв `mtg_fd:*`) — прямого аналога `msg_fes:clm`/`msg_fes:cth` для MTG на публичном WMS `view.eumetsat.int` НЕТ. Есть только RGB-композиты: `rgb_cloudphase`, `rgb_cloudtype`, `rgb_geocolour`, `rgb_truecolour`, `rgb_dust`, `rgb_fog`, `rgb_snow`, `rgb_firetemperature`. Настоящие численные MTG CLM/CTTH существуют только как L2 NetCDF-продукты через EUMETSAT Data Store (`data.eumetsat.int`, другой протокол — eumdac/API, не GetMap) — отдельная задача уровня "новая интеграция", не правка URL.
Дополнительно: EUMETSAT продолжает параллельно генерировать MSG Cloud Mask/CTH "until further notice, or until end of MSG 0° services" — миграция не горит.
Решение: задачу закрыть. `msg_fes:clm`/`msg_fes:cth` остаются источником для `eumetsat_cloud_forecast.py`. RGB-слои MTG уже используются отдельно и по назначению:
  - `rgb_cloudphase` + `rgb_cloudtype` → `scripts/eumetsat_cloud_phase_type.py` (фаза/грубый тип облаков, HSV-анкеры "на глаз", не откалибровано — см. `unclassified_fraction` в debug-файле)
  - `rgb_geocolour` → `scripts/eumetsat_geocolour_motion.py` (движение + area-fraction круглосуточно, день/ночь разные ветки классификации, с фильтром городских огней)


## 2026-08-02: тот же баг радиуса — в ИК-блоке (mtg_fd:ir105_hrfi), плюс баг без-порогового "облака"
`eumetsat_ir_motion.py` содержал ДВЕ проблемы, найденные по живому скриншоту (полностью однородный тёмный кадр, "ясно" по факту):
1. `station_state` считался в LOCAL_RADIUS_KM=50 (той же маске, что и региональный тренд area/brightness) — тот же класс бага, что чинили в `eumetsat_cloud_forecast.py`. Фикс: добавлен общий `STATE_RADIUS_KM=12` и `fc.station_area_mask()` в `field_motion_common.py` (переиспользуемый), `station_state` теперь считается по нему.
2. `cloud_mass_distance_km` ("Основная облачная масса") находился ВСЕГДА — порог был 90-й перцентиль ВНУТРИ кадра, у которого нет абсолютного пола: даже в полностью однородной сцене без единого настоящего облака "10% самых тёплых пикселей" всё равно где-то есть (рельеф/берег/обычный прогрев) и `nearest_of_type()` находил связный blob ≥40px и репортил его как "облачную массу" с движением/скоростью. Фикс: добавлена проверка контраста — 90-й перцентиль должен отличаться от медианы кадра минимум на `MIN_CLOUD_CONTRAST_SIGMA=1.2` std кадра, иначе `cloud_mass_distance_km=None` + `cloud_mass_verdict="значимой облачной массы в поле зрения нет"`.
Также по просьбе убран блок "Область анализа" (окно/центр/радиус) из рендера ИК-блока в `nearby_precip.js` — избыточная техническая информация.

## 2026-08-02: тот же баг радиуса — в блоке GeoColour (mtg_fd:rgb_geocolour)
Подтверждена ровно та же проблема, что чинили в CLM и IR: `station_state` в `eumetsat_geocolour_motion.py` считался по `fc.local_area_mask()` (LOCAL_RADIUS_KM=50, та же маска, что и региональный тренд area_fraction). Фикс: добавлена отдельная `state_fracs` по `fc.station_area_mask()` (STATE_RADIUS_KM=12), `station_state`/`station_area_fraction` теперь считаются по ней; `area_fracs` (50км) остался только для регионального тренда/гейта motion (`MIN_CLOUD_FRACTION_FOR_MOTION`).
Второй IR-баг (без-порогового "облака" из-за перцентиль-порога) сюда НЕ относится: `_classify_cloud()` в GeoColour и так строит `is_cloud` через абсолютную HSV-классификацию (день: низкая S/высокая V; ночь: голубой hue-диапазон), а не через относительный перцентиль внутри кадра — `nearest_of_type()` уже получает физически осмысленную бинарную маску, "пустого" ложного blob'а там в принципе не возникает.
Закоммичено в `scripts/eumetsat_geocolour_motion.py`.


## 2026-08-02: разбор жалобы «контуры gif не совпадают с картой-подложкой, точка станции съезжает при приближении»
Жалоба касалась широкой обзорной MP4-петли в `eumetsat.html` (BBOX 22-40°E/40-52°N, см. `eumetsat_anim_render.py`), не пиксельного анализа вокруг станции.

**Проверено и НЕ баг:** `ANIM_BOUNDS` в `eumetsat.js` и `BBOX` в `eumetsat_anim_render.py` совпадают 1:1 `(22.0, 40.0, 40.0, 52.0)` — привязка растра к карте корректна на уровне кода.

**Вероятная причина (не код, а данные):** `msg_fes:clm` (Cloud Mask) — продукт с нативным разрешением SEVIRI ~3-6км (для Одессы хуже среднего — она не в надире диска MSG 0°). Собственная land/sea классификация ВНУТРИ этого продукта физически не может повторить тонкий контур берега/лиманов, который OSM рисует на порядки точнее. При сильном приближении блочность становится заметнее — создаёт ощущение, что маркер станции «съезжает», хотя его реальные координаты не меняются (Leaflet-маркер всегда точен). Это ограничение источника данных, зум тут ничего не чинит.

**Попутно найден и пофикшен реальный баг** — в другом месте, но напрямую влияющий на «расстояние до облака от станции»: `pixel_to_km_offset()` в `field_motion_common.py` (используется `nearest_of_type()` для `cloud_mass_distance_km`/`bearing` во ВСЕХ `*_motion.py`-скриптах: cloud_forecast, ir_motion, geocolour_motion) использовал edge-to-edge конвенцию пиксельной сетки (`frac=col/(TILE_SIZE-1)`, пиксель 0 ровно на границе bbox), а не pixel-as-area конвенцию (пиксель 0 — область шириной 1/TILE_SIZE окна), как в `local_area_mask()`/`station_area_mask()` того же файла — то есть ДВЕ разные конвенции сетки внутри одного модуля. Расхождение росло от 0 в центре 5°-окна до ~0.5км на его краю (192км от станции). Фикс: `pixel_to_km_offset()` переведён на ту же конвенцию (`center=(TILE_SIZE-1)/2`, шаг `KM_PER_PX_*`), что и остальные функции модуля. Закоммичено в `scripts/field_motion_common.py`.

## 2026-08-02: единая точка настройки охвата GIF-просмотрщика (eumetsat.html)
Запрос: возможность увеличить охват территории и чтобы координаты охвата менялись в ОДНОМ месте для всех каналов сразу.

**Что было:** `BBOX` в `scripts/eumetsat_anim_render.py` уже был единой точкой для всех 11 каналов на Python-стороне (общий цикл по `LAYERS`), но дублировался вручную в `eumetsat.js` (`ANIM_BOUNDS`) с комментарием "не забудь поменять и там" — источник потенциального рассинхрона. Плюс `WIDTH,HEIGHT=1000,666` были захардкожены отдельно от `BBOX`, посчитаны из ГРАДУСНОГО соотношения (18°:12°=1.5), а не из реальных км — на широте Одессы градус долготы короче градуса широты, поэтому пиксели видео были не квадратными (км/px по X ≈1.39, по Y ≈2.0 — лёгкое искажение).

**Заодно нашёл и пофикшен баг-дубликат:** в `eumetsat_cloud_forecast.py` была СОБСТВЕННАЯ копия `_pixel_to_km_offset` с той же старой edge-to-edge ошибкой, что чинили в `field_motion_common.py` (см. выше) — фикс туда не долетел именно из-за дублирования кода. Заменена на прямой вызов `fc.pixel_to_km_offset`.

**Сделано:**
1. `scripts/eumetsat_anim_render.py`: `WIDTH,HEIGHT` больше не константы — считаются функцией `_bbox_dimensions(BBOX, TARGET_KM_PER_PX)` из фактических км-размеров BBOX (не градусов), с округлением до чётных (требование libx264). Новый охват даёт 928×892 (было 1000×666) — заодно исправляет неквадратность пикселей.
2. `BBOX` — теперь ЕДИНСТВЕННОЕ место для изменения охвата на сервере; при увеличении охвата видео-файлы станут больше/рендер дольше (пропорционально площади), но разрешение на пиксель (`TARGET_KM_PER_PX=1.5`) не деградирует само по себе.
3. Границы публикуются в `data/anim/manifest.json` (ключ `_bounds`, формат `[[lat_min,lon_min],[lat_max,lon_max]]`).
4. `eumetsat.js`: `ANIM_BOUNDS` стал `let` с дефолтом только на время до первой загрузки манифеста; `loadManifest()` подхватывает `_bounds` из манифеста и, если охват реально изменился, перецентровывает карту (`fitToAnimBounds()`) и обновляет `setBounds()` у текущего video overlay.

**Важно (ограничение, о котором просили не забыть):** это касается только ШИРОКОГО обзорного охвата для просмотра (`eumetsat_anim_render.py`, `eumetsat.html`). УЗКОЕ окно анализа станции (`field_motion_common.py`: `CENTER_LAT/LON`, `HALF_WINDOW_DEG=2.5°`, `TILE_SIZE=400`), от которого зависят `cloud_forecast.py`/`ir_motion.py`/`geocolour_motion.py`/`cloud_phase_type.py`, — ОТДЕЛЬНАЯ, уже единая точка (все скрипты импортируют `fc` и берут константы оттуда), но НЕ трогалась намеренно: расширение этого окна означало бы, что все персистентные `.npz`-буферы (`data/eumetsat_*_buffer.npz`) теряют совместимость с новой сеткой и должны накапливаться заново с нуля (bootstrap) — если понадобится расширить именно это окно, нужно явно это обсудить отдельно.

## 2026-08-02: диагностика "зависания" лога после eumetsat_geocolour_motion.py

Жалоба: в логе run-satellite после последней строки `[OK] eumetsat_geocolour_motion.py` наступает долгая тишина (job числится Started несколько минут), выглядит как зависание.

**Не баг, а немой шаг конвейера.** Порядок вызовов в `scripts/gh_satellite_pipeline.py::main()`: ...precip_motion → geocolour_motion → **check_eumetsat_anim_render()** → git_push. Именно `eumetsat_anim_render.py` идёт следующим и молчит дольше всех:
- Гейт 20 мин (реже остальных 5-15-минутных), поэтому срабатывает не в каждом прогоне — когда срабатывает, это самый тяжёлый шаг.
- На каждый из 13 слоёв `LAYERS` (`scripts/eumetsat_anim_render.py`): 1 запрос `GetCapabilities` (`get_layer_latest_time`, timeout=25с) + до 13 ПОСЛЕДОВАТЕЛЬНЫХ `GetMap`-запросов (`fetch_map_custom`, TIMEOUT=25с, retries=2, delay=4с — то есть до ~54с на один неотвечающий кадр) + `ffmpeg` кодирование ролика.
- `render_layer()` печатает `[OK]/[WARN]` только ОДИН РАЗ — когда весь ролик слоя полностью готов (скачаны все кадры + отработал ffmpeg). Прогресса по кадрам внутри слоя в лог не идёт.
- Итого: до 13 слоёв × (25с capabilities + до 13×54с worst-case на кадры) — в худшем случае это реально многие минуты полной тишины в логе между `[OK] geocolour_motion` и первым `[OK] eumetsat_anim_render.py: <layer>`. Job timeout всего шага 600с (10 мин, `subprocess.run(..., timeout=600)`), общий job timeout экшена — 20 мин.

## 2026-08-05: слой конфликтов — eumetsat_target_summary.py

Новый скрипт `eumetsat_target_summary.py` — читает `target_confirmation`
всех 5 модулей + primary target из `cloud_forecast.json`, сводит в ОДНО
место (`data/eumetsat_target_summary.json`) вместо ручной сверки 5 файлов.
Запускается в `gh_satellite_pipeline.py` после всех пяти confirming-модулей,
перед `check_eumetsat_anim_render()`. Дёшево (только чтение локальных JSON,
без WMS-фетча) — гейта по времени нет, гоняется каждый цикл.

Два разных вопроса разведены явно, не смешиваются в одну цифру:
1. **existence** (трио ir_motion/geocolour_motion/cloud_phase_type,
   порог confirmed у каждого 0.5) — "существует ли вообще цель".
   `consensus`: `confirmed` (все за) / `not_confirmed` (все против,
   вероятно ложное срабатывание CLM) / `disputed` (расхождение —
   именно этот случай раньше терялся, ради него всё затевалось) /
   `insufficient_data` (0 модулей отдали голос).
2. **phenomena** (precip_forecast/lightning_forecast, свои низкие пороги
   0.05/0.02) — отдельные да/нет-факты про уже найденную цель, не
   участвуют в голосовании существования.

Плюс rule-based `verdict` — черновая версия шага 7 задуманного алгоритма
(человекочитаемое предложение, собирающее всё выше). При `disputed` и
несогласии именно `cloud_phase_type` — добавляет подсказку про ночь, но
ТОЛЬКО если сейчас реально ночь (проверено локальной `_is_night()`, не
переиспользует `fc.is_daytime()` — у неё другой формат таймстемпа, не
хотелось менять контракт ради одного вызова).

**Протестировано локально перед пушем** (реальные JSON с GitHub, не
синтетика): нормальный случай (disputed, 1 за / 2 против, реальные живые
данные), пустой `candidates` (`status: no_target`), отсутствие
`cloud_forecast.json` целиком (`status: no_data`), отсутствие одного из
5 модулей (`confirmed: null`, не роняет consensus по остальным двум).
Все кейсы отработали без падений. Один найденный на тестах баг —
изначально текст про "частая причина — ночь" выводился безусловно, даже
днём (реальный тестовый прогон в 03:47 UTC = 06:47 Одесса, disputed по
другой причине) — пофикшено до пуша.

Добавлен в whitelist коммита `gh_satellite_pipeline.py`
