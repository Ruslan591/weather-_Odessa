# Тема: Объективная линия фронта по сети наземных станций

_Последнее обновление: 2026-09-03_

## Что это

Развитие спутникового трекинга фронтов (см. `docs/topics/eumetsat.md`) —
вместо/в дополнение к визуальному прокси по форме облака (проекция
near-tier системы на far/very_far снимок, покраска реальных пикселей blob'а,
см. `eumetsat_far_watch.py::_mark_found_systems_on_far_image`, eumetsat.md)
пробуем вычислить объективную линию фронта по полю температуры/ветра/
давления с сети наземных станций.

## Контекст решения (2026-09-03)

- **Развилка**, обсуждённая с пользователем:
  - (А) узкая доводка уже начатой ahead/behind-верификации (см.
    `ground_station_selector.py`, план от 2026-08-14) — просто сравнение
    2 станций по курсу трека (упал ли temp, сменился ли ветер), без
    построения полноценной линии.
  - (Б) полноценная интерполяция поля по многим станциям → градиент →
    гребень максимума = объективная линия фронта.
  - **Выбран вариант Б.**
- Skeleton-подход (медианная ось формы облака через scikit-image,
  предложен Claude ранее 2026-09-03) — **отложен** пользователем в пользу
  варианта Б. Не отменён — может вернуться как fallback/доп. слой, если
  станций для интерполяции окажется мало.
- **Источник данных — BUFR, не SYNOP, приоритетно.** В Европе многие
  станции шлют BUFR автоматически почасово (уже подтверждено на практике,
  см. находку 2026-08-16 в `fetch_bufr_obs.py`: FETESTI/WMO 15444 и
  MAHMUDIA/WMO 15337 перестали слать классический SYNOP на ogimet, но
  продолжают слать почасовой автоматический BUFR через Meteomanz тем же
  WMO-индексом). SYNOP — **fallback**, и то только если BUFR недоступен
  **И** текущее время достаточно близко к синоптическому сроку (00/03/06/
  09/12/15/18/21 UTC ± задержка публикации) — иначе дёргать его смысла
  нет, SYNOP обновляется раз в 3ч.
- **ВАЖНО, чтобы не перепутать с существующим кодом:** это НЕ тот же
  приоритет, что уже реализован в `eumetsat_ground_station_verify.py::
  _get_or_fetch()` — там СНАЧАЛА SYNOP/ogimet, BUFR только фолбэк, если
  SYNOP не ответил (обратный порядок!). Тот код обслуживает УЗКУЮ
  ahead/behind-верификацию (2 станции на трек, вариант А выше) — его
  логику приоритета сознательно НЕ трогаем, пока не попросят явно.
  BUFR-first — порядок только для НОВОЙ фичи (полевая интерполяция по
  многим станциям), описанной в этом файле.
- BUFR-источник — **Meteomanz** (не ogimet):
  `fetch_bufr_obs.py::fetch_latest_bufr_essentials(station_id, hours_back)`
  — уже обобщён на произвольный `station_id` (не только 33837 Одесса),
  переиспользуем как есть, писать заново не нужно.

## Уже готовая инфраструктура (переиспользуем, не пишем заново)

- **`data/ground_stations.json`** — 140 станций (UP=30, MD=20, RO=87,
  BU=3), поля `name/ctry/lat/lon/elev_m/dist_km_from_odessa/
  wmo_synop_id/icao/source`. Дистанции от Одессы 7.4-498км, медиана
  ~338км — то есть плотность в основном соответствует масштабу far-tier
  (~1000км), а не very_far (~2500км).
- **`fetch_bufr_obs.py::fetch_latest_bufr_essentials(station_id,
  hours_back=4)`** — почасовой BUFR с Meteomanz, возвращает essentials-
  словарь (temp/station_pressure/sea_pressure/wind_dir_deg/
  wind_speed_ms/precip_mm/present_weather_code/present_weather_label/
  is_extreme_weather/obs_source="BUFR"), работает для ЛЮБОЙ станции.
- **`ground_station_obs_fetch.py::fetch_latest_obs(station_id,
  hours_back=9)`** — SYNOP через ogimet (+ 2 прокси-фолбэка), та же
  форма essentials, `obs_source="SYNOP"`.
- **`ground_station_selector.py::select_ahead_behind()`** — геометрия
  dx/dy/along_km/perp_km относительно центра Одессы и оси движения
  трека; пригодится частично — например, для сверки "похожа ли
  объективная линия на уже известный трек".

## На горизонте (план, ничего из этого ещё не начато)

1. Новый скрипт (рабочее имя `ground_station_field_fetch.py`) — обходит
   станции из `ground_stations.json`, для каждой: BUFR первым
   (`fetch_latest_bufr_essentials`), SYNOP вторым (только если BUFR
   пуст И сейчас близко к синоптическому сроку). Кэш по станции с TTL
   (по аналогии с `STALE_MINUTES=45` в `eumetsat_ground_station_verify.
   py`) — 140 последовательных сетевых fetch каждый 5-минутный цикл VPS
   недопустимо ни по времени, ни по нагрузке на Meteomanz/ogimet.
2. Интерполяция поля температуры (scipy `griddata`/`RBF`) по успешно
   полученным станциям на регулярную сетку (та же geo-привязка, что у
   far/very_far — `fc.CENTER_LAT/CENTER_LON`, `fc.KM_PER_DEG_LAT/LON`).
3. Градиент поля, поиск гребня максимума градиента — кандидат в линию
   фронта.
4. Кросс-проверка по смене направления ветра вдоль гребня (тёплый/
   холодный фронт).
5. Куда рисовать результат (far/very_far снимок? отдельная карта совсем
   без спутника, просто станции+интерполяция?) — решить отдельно, после
   того как сам расчёт линии на реальных данных даст разумный результат.

## Открытые вопросы

- Сколько станций реально фетчить за цикл — 140 сразу дорого по
  времени/рейт-лимитам источников. Варианты: ограничить подмножеством
  (например, только в разумном коридоре вокруг предполагаемого
  положения фронта, по аналогии с ahead/behind), либо разносить fetch по
  времени (не все сразу, кэш+ротация по TTL).
- Частота пересчёта поля — не каждые 5 минут (сеть/лимиты), вероятно раз
  в синоптический срок или раз в 30-60 минут.
- Не все 140 станций одинаково надёжны/актуальны — часть SYNOP уже
  "умерла" (см. находку по FETESTI/MAHMUDIA), BUFR может отсутствовать у
  части станций тоже. Реальное покрытие для интерполяции может оказаться
  заметно реже 140 точек — предположение, не проверено на практике.
- Разрешение станционной сети (десятки-сотни км между станциями)
  физически не позволит поймать резкий фронт, прошедший ровно между
  двумя станциями — интерполяция его "размажет". Это ограничение метода,
  не баг реализации.
