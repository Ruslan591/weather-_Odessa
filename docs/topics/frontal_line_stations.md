# Тема: Объективная линия фронта — три независимые позиции сравнения

_Последнее обновление: 2026-09-03_

## Что это

Развитие спутникового трекинга фронтов (см. `docs/topics/eumetsat.md`).
Визуальный прокси по форме облака на far/very_far снимке
(`eumetsat_far_watch.py::_mark_found_systems_on_far_image`) **испробован и
УДАЛЁН** 2026-09-03 — на масштабе ~1000-2500км облачность физически один
слипшийся континентальный массив, даже с локальным окном результат не
устроил пользователя ("убери, однозначно"). См. eumetsat.md за историю
попытки, здесь эта ветка больше не описывается.

Взамен — попытка вычислить объективную линию фронта, сверяя **три
независимые позиции**:
1. **Спутник** — форма/ось уже найденной near-tier системы
   (`eumetsat_frontal_track.json`) — что реально видно на снимке.
2. **Open-Meteo** — плотное поле температуры/ветра НЕСКОЛЬКИХ моделей
   (батч-запросы, до 100 точек за раз, разрешение 1-11км — гуще, чем сеть
   станций) — где МОДЕЛИ считают, что проходит фронт. Ещё не начато.
3. **BUFR/SYNOP наземных станций** — реальная правда в редких точках, для
   проверки/выбора между версиями (1) и (2), а не как основа для
   интерполяции (см. "Смена архитектуры" ниже).

## Смена архитектуры (2026-09-03)

Изначальный план (вариант Б из первой версии этого файла — интерполяция
ТОЛЬКО по 140 станциям) поставлен под сомнение пользователем: сеть станций
слишком редкая и дырявая (спейсинг 50-150км, часть SYNOP уже "умерла", не
все BUFR отвечают). Рассмотрена альтернатива — использовать поле
Open-Meteo вместо станций, но и тут есть проблема: Open-Meteo — это ВЫВОД
МОДЕЛИ, а весь проект по своей философии сравнивает модели С РЕАЛЬНОСТЬЮ
(SYNOP на 33837), а не доверяет им как истине. Densely resolved линия,
посчитанная из GFS, может быть просто красиво нарисованной ошибкой GFS.

**Итоговое решение**: не выбирать одно, а держать оба источника, но в
РАЗНЫХ ролях:
- Open-Meteo (плотная сетка, дёшево, батчами) → черновая линия фронта по
  градиенту поля — простой и быстрый в реализации шаг, без дыр в
  покрытии, которые есть у станций.
- Реальные BUFR/SYNOP станции (уже почти готовая инфраструктура,
  `ground_station_field_fetch.py`) → НЕ основа для интерполяции, а
  **независимый судья**: в нескольких точках вдоль черновой линии
  сверяем, действительно ли реальные данные подтверждают перепад
  temp/ветра именно там, и (бонус, укладывается в существующий скоринг
  моделей проекта) — какая из 8 моделей точнее положила фронт в этой
  точке.

Это делает три позиции (спутник/Open-Meteo/станции) взаимно проверяющими
друг друга, а не дублирующими.

## Контекст решения — исходная развилка (2026-09-03, для истории)

- **Развилка**, обсуждённая с пользователем:
  - (А) узкая доводка уже начатой ahead/behind-верификации (см.
    `ground_station_selector.py`, план от 2026-08-14) — просто сравнение
    2 станций по курсу трека (упал ли temp, сменился ли ветер), без
    построения полноценной линии.
  - (Б) полноценная интерполяция поля по многим станциям → градиент →
    гребень максимума = объективная линия фронта.
  - Выбран вариант Б, но затем **архитектура пересмотрена** — см. раздел
    "Смена архитектуры" выше. Станции остаются, но не как источник
    интерполяции, а как проверка.
- Skeleton-подход (медианная ось формы облака через scikit-image,
  предложен Claude ранее 2026-09-03) — **отложен** пользователем в пользу
  варианта Б. Не отменён — может вернуться как fallback/доп. слой.
- **Источник данных станций — BUFR, не SYNOP, приоритетно.** В Европе
  многие станции шлют BUFR автоматически почасово (уже подтверждено на
  практике, см. находку 2026-08-16 в `fetch_bufr_obs.py`: FETESTI/WMO
  15444 и MAHMUDIA/WMO 15337 перестали слать классический SYNOP на
  ogimet, но продолжают слать почасовой автоматический BUFR через
  Meteomanz тем же WMO-индексом). SYNOP — **fallback**, и то только если
  BUFR недоступен **И** текущее время достаточно близко к синоптическому
  сроку (00/03/06/09/12/15/18/21 UTC ± задержка публикации).
- **ВАЖНО, чтобы не перепутать с существующим кодом:** это НЕ тот же
  приоритет, что уже реализован в `eumetsat_ground_station_verify.py::
  _get_or_fetch()` — там СНАЧАЛА SYNOP/ogimet, BUFR только фолбэк, если
  SYNOP не ответил (обратный порядок!). Тот код обслуживает УЗКУЮ
  ahead/behind-верификацию (2 станции на трек, вариант А выше) — его
  логику приоритета сознательно НЕ трогаем, пока не попросят явно.
  BUFR-first — порядок только для НОВОЙ фичи (`ground_station_field_
  fetch.py`), описанной в этом файле.
- BUFR-источник — **Meteomanz** (не ogimet):
  `fetch_bufr_obs.py::fetch_latest_bufr_essentials(station_id, hours_back)`
  — уже обобщён на произвольный `station_id` (не только 33837 Одесса),
  переиспользуем как есть, писать заново не нужно.
- **НАХОДКА 2026-09-03, подтверждена вживую (через Termux пользователя —
  сеть Meteomanz недоступна из песочницы Claude ни для bash_tool, ни для
  web_fetch):** Meteomanz на ОДНОМ И ТОМ ЖЕ URL (`sy1?ty=hd&ind=...`)
  отдаёт ОБА типа отчёта в зависимости от станции/срока — маркер в HTML:
  - `"BUFR report, by an automatic station."` — текущий парсер
    (`fetch_bufr_obs.py::parse_obs`) уже это ловит (проверено на FETESTI/
    15444, срок 03Z — даже классический синоптический час, автоматическая
    станция репортит непрерывно).
  - `"Synop, reported by a manned station."` — **пока НЕ парсится**,
    текущий код это отбрасывает как "нет данных" (проверено на TIRASPOL/
    33829, срок 03Z). Разметка полей ЗЕРКАЛЬНАЯ относительно BUFR-ветки:
    `<i><b>Label: </b></i>значение<br>` (у BUFR — `<b><i>Label: </i></b>`,
    italic внутри bold, здесь наоборот). Формат значений заметно менее
    машиночитаемый, чем BUFR-дескрипторы: непостоянные пробелы в лейблах
    (`"Air Temperature : "`, `"Present and past                    weather: "`),
    диапазоны в одном поле (`"Wind direction: "` → `"305º-314º
    (northwest)."`), два значения в одном поле (`"Middle clouds: "` →
    `"altocumulus translucidous (mostly transparent). (Cover: 2
    eighths)."`), октаты словом (`"2 eighths"`, не числом). Реальный
    образец сохранён для тестирования — см. план ниже, "Заменить ogimet".
  - Это **независимо подтверждает** внешний источник (не сам Meteomanz):
    "Meteomanz provides observed weather data... obtained from SYNOP and
    BUFR messages" — то есть архитектурно один источник для обоих типов,
    не совпадение для конкретно этих двух станций.

## Уже готовая инфраструктура (переиспользуем, не пишем заново)

- **`data/ground_stations.json`** — 140 станций (UP=30, MD=20, RO=87,
  BU=3), поля `name/ctry/lat/lon/elev_m/dist_km_from_odessa/
  wmo_synop_id/icao/source`. Дистанции от Одессы 7.4-498км, медиана
  ~338км — то есть плотность в основном соответствует масштабу far-tier
  (~1000км), а не very_far (~2500км).
- **`fetch_bufr_obs.py::fetch_latest_bufr_essentials(station_id,
  hours_back=4)`** — почасовой BUFR с Meteomanz, возвращает essentials-
  словарь (temp/station_pressure/sea_pressure/wind_dir_deg/
  wind_speed_ms/precip_mm/present_weather_code/present_weather_label/
  is_extreme_weather/obs_source="BUFR"), работает для ЛЮБОЙ станции.
- **`ground_station_obs_fetch.py::fetch_latest_obs(station_id,
  hours_back=9)`** — SYNOP через ogimet (+ 2 прокси-фолбэка), та же
  форма essentials, `obs_source="SYNOP"`.
- **`ground_station_selector.py::select_ahead_behind()`** — геометрия
  dx/dy/along_km/perp_km относительно центра Одессы и оси движения
  трека; пригодится частично — например, для сверки "похожа ли
  объективная линия на уже известный трек".

## На горизонте (план)

1. ~~Новый скрипт... BUFR первым... SYNOP вторым... кэш по станции с TTL~~
   — **СДЕЛАНО 2026-09-03**: `ground_station_selector.py::
   generate_axis_samples()` (геометрия — точки вдоль оси вытянутости
   трека) + `ground_station_field_fetch.py` (обход сэмплов, BUFR-first/
   SYNOP-fallback-у-синоптического-срока через ogimet, кэш по
   wmo_synop_id с TTL=45мин в `data/ground_station_field.json`).
   Подключено в `vps_satellite_pipeline.py` (боевой) сразу после
   `check_eumetsat_ground_station_verify`, output-файл в whitelist
   коммита. Проверено на реальных данных треков с мок-сетью: сэмпл
   offset=0 воспроизводит ту же пару ahead/behind, что уже независимо
   посчитана в самом треке (LIUBASHIVKA/CEADIR-LUNGA для track_id=892) —
   геометрия переиспользована корректно; кэш подтверждён (повторный
   прогон без сетевых вызовов). **Не проверено вживую с реальным
   Meteomanz/ogimet** — сеть недоступна из песочницы Claude, только с
   мок-функциями. Первый боевой прогон на VPS покажет реальное покрытие.
   Роль этого шага теперь ИЗМЕНИЛАСЬ (см. "Смена архитектуры" выше) —
   это больше не источник для интерполяции, а проверочный слой для
   шагов 3-4 ниже.
2. ~~Заменить ogimet на Meteomanz SYNOP~~ — **СДЕЛАНО 2026-09-03**.
   `fetch_bufr_obs.py::parse_synop_essentials_from_meteomanz()` — парсер
   ручной SYNOP-ветки (маркер `"Synop, reported by a manned station."`),
   протестирован на реальном образце (TIRASPOL/33829, 03Z 2026-09-02) —
   все поля (temp/давление/тенденция/ветер/облачность) совпали с ручным
   разбором образца, плюс граничные тесты (BUFR-парсер не путает SYNOP-
   текст и наоборот, детекция опасных явлений по ключевым словам,
   осадки с реальным значением). `present_weather_code` сознательно
   оставлен `None` — эта ветка Meteomanz даёт только текст, не числовой
   код ВМО; `is_extreme_weather` — эвристика по английским ключевым
   словам (`EXTREME_WEATHER_KEYWORDS_EN`), не точное соответствие
   таблице. `pressure_tendency_code` подтверждён вживую только для
   простого случая (код 2) — составные тенденции (коды 0,1,3,5,6,8,
   "then decreasing"/"then steady" и т.п.) сознательно НЕ реализованы,
   нет реальных образцов текста для них, возвращают `None`, а не догадку.

   Новая функция `fetch_bufr_obs.py::fetch_latest_meteomanz_essentials()`
   — ОДИН HTTP-запрос пробует ОБА парсера (BUFR и SYNOP) на одном и том
   же ответе (это буквально одна и та же страница Meteomanz, см.
   находку выше) — больше не нужны ни отдельный SYNOP-fallback-запрос,
   ни гейт по синоптическому сроку. `ground_station_field_fetch.py`
   переписан на эту единую функцию, ogimet-логика (`_near_synoptic_
   hour()`, импорт `ground_station_obs_fetch.fetch_latest_obs`) удалена
   целиком. Проверено мок-тестом на реальных данных 3 треков — то же
   поведение (3 трека/11 сэмплов/12 уникальных станций), что и до
   упрощения.

   `eumetsat_ground_station_verify.py` (узкая ahead/behind-верификация)
   НЕ тронут — по-прежнему использует ogimet первым, BUFR-фолбэк
   отдельно; решение не менять его логику осталось в силе (см. выше).
3. ~~Open-Meteo — плотное поле для черновой линии~~ — **СДЕЛАНО
   2026-09-03**: `open_meteo_field_fetch.py` — 2D-сетка (не 1D вдоль оси,
   как у станций) вокруг трека, шаг 40км, ≤100 точек/модель (лимит
   Open-Meteo), батч через `current=` по 8 моделям проекта (id сверены с
   фактическим вызовом в `update.py`, не metaId — это разные вещи).
   Градиент — `np.gradient()` прямо по сетке (интерполяция не нужна,
   значения уже на сетке). `ridge_perp_index` — простейшая черновая линия
   (по одной точке на along-строку, argmax градиента поперёк оси), БЕЗ
   сглаживания — первая версия. Подключено в `vps_satellite_pipeline.py`
   после `ground_station_field_fetch`, output в whitelist. Протестировано
   геометрия+градиент на синтетике и `main()` целиком на реальных треках
   с мок-фетчем — 3 трека × 8 моделей, сетки ≤100 точек. **Не проверено с
   реальным Open-Meteo** — домен не в сетевом allowlist песочницы Claude.
   Первый боевой прогон на VPS покажет реальные данные/формат ответа. Батч-
   запросы (до 100 точек за раз, лимит 10000/день на некоммерческом
   доступе), поле температуры/ветра на регулярной сетке вокруг найденной
   near-tier системы, из НЕСКОЛЬКИХ моделей (те же 8, что уже
   используются в проекте для скоринга) — не только "best_match".
   Разрешение моделей 1-11км (у ICON-EU/D2 — 2-7км) — гуще, чем сеть
   станций. Градиент поля → гребень максимума = кандидат в линию фронта.
   Это ЧЕРНОВАЯ линия — отражает мнение МОДЕЛИ, не реальность (весь
   проект по философии сравнивает модели с правдой, а не доверяет им
   напрямую — см. "Смена архитектуры").
4. **Сверка по станциям** (не начато, но `_diagnostics()` в
   `ground_station_field_fetch.py` уже частично для этого готов —
   считает `temp_diff_behind_minus_ahead`/`wind_dir_shift_deg`/
   `pressure_diff_behind_minus_ahead` для каждого сэмпла вдоль оси). В
   нескольких точках вдоль черновой линии (шаг 3) сверяем реальными

   из 8 моделей точнее положила фронт в этой конкретной точке (та же
   логика, что уже используется в проекте для скоринга точности
   прогноза, применённая к положению фронта).
5. Куда рисовать итоговый результат (три слоя — спутник/модель/станции)

## Отменённые/испробованные и отвергнутые подходы

- **Покраска реальной формы на far/very_far** (`eumetsat_far_watch.py::
  _mark_found_systems_on_far_image`) — реализована 2026-09-02, дважды
  исправлена (сначала глобальная связность красила пол-Европы, потом
  локальное окно), но пользователь решил убрать метод полностью
  2026-09-03 ("убери, однозначно") — результат всё равно не соответствовал
  ожиданиям. Код удалён из `eumetsat_far_watch.py` целиком (функция,
  вызов, неиспользуемые импорты math/PIL.ImageDraw/scipy.ndimage), подпись
  на фронтенде тоже убрана. Не возвращаться к этому подходу без явного
  запроса — вопрос закрыт.
- **Интерполяция ТОЛЬКО по станциям** (исходный вариант Б) — не отменена
  полностью, но роль изменена на "проверка", а не "основа" (см. "Смена
  архитектуры" выше). Причина — редкая/дырявая сеть (140 станций,
  спейсинг 50-150км, часть SYNOP уже "умерла").

## Открытые вопросы

- ~~Сколько станций реально фетчить за цикл~~ — **решено 2026-09-03**:
  не все 140 сразу и не произвольное подмножество, а только станции,
  попадающие в ahead/behind по каждой из точек `generate_axis_samples()`
  вдоль оси УЖЕ найденного трека (обычно 3-11 сэмплов на трек × 2
  станции, с дедупликацией повторов через кэш).
- Частота пересчёта — не каждые 5 минут (сеть/лимиты), вероятно раз
  в синоптический срок или раз в 30-60 минут. Актуально и для станций, и
  для Open-Meteo (хоть лимит там щедрее — 10000/день, но незачем дёргать
  чаще, чем меняется картина).
- Не все 140 станций одинаково надёжны/актуальны — часть SYNOP уже
  "умерла" (см. находку по FETESTI/MAHMUDIA), BUFR может отсутствовать у
  части станций тоже. Для РОЛИ "проверка" (не "основа") это менее
  критично, чем было бы для чистой интерполяции — достаточно, чтобы
  хватало станций в нескольких контрольных точках, не по всей линии.
- Разрешение станционной сети (десятки-сотни км между станциями)
  физически не позволит поймать резкий фронт, прошедший ровно между
  двумя станциями — для роли "проверка" это означает, что не каждая
  контрольная точка вдоль черновой (Open-Meteo) линии сможет быть
  подтверждена станцией — часть точек останется без независимой сверки.
- Open-Meteo — это МОДЕЛЬ, не истина (см. "Смена архитектуры"). Открыт
  вопрос: если станции В КОНКРЕТНОЙ точке ПРОТИВОРЕЧАТ черновой линии
  (перепада нет там, где модель его рисует) — как это интерпретировать?
  Модель ошиблась, или станция просто не подтверждает локально (шум)?
  Нужна методика, ещё не продумана.
- Не решено, с какого именно эндпоинта/параметров Open-Meteo брать поле
  (обычный forecast API на почасовой сетке точек? ensemble API? какие
  именно переменные — temperature_2m/dewpoint/wind_u10/wind_v10?) — надо
  проверить перед реализацией шага 3.
