# Миграция хостинга: перенос compute-слоя с GitHub Actions на VPS

## Purpose & context

Текущий пайплайн (`gh_pipeline.py`, `gh_satellite_pipeline.py`, `gh_ai_pipeline.py`) работает целиком на GitHub Actions: Termux (job 1001, каждые 15 мин) шлёт только лёгкий `workflow_dispatch`-триггер, вся реальная работа — на эфемерных раннерах GitHub. Git используется как единственная база данных и IPC между тремя независимыми скриптами (каждый коммитит и пушит в main сам по себе).

22–23.08.2026 при диагностике зависшего Gemini-видео вскрылись структурные боли этой архитектуры:
- **Гонки при пуше** — независимые коммиты от разных пайплайнов иногда «склеиваются» GitHub в одно push-событие, путается атрибуция в UI Actions (see `docs/topics/main_pipeline.md` при необходимости деталей инцидента).
- **Логи Actions недоступны напрямую** — редиректятся на `blob.core.windows.net`, домен не в whitelist сети Claude; пришлось городить временный debug-шаг, пишущий stderr в файл репозитория через API.
- **Отсутствие персистентности** — раз у эфемерных раннеров нет своего диска между запусками, весь стейт вынужденно тащится через git commit — отсюда рост `.git` и общая хрупкость.
- **Дублирование зависимостей** — numpy был прописан в одном workflow (`make_video.yml`) и забыт в другом (`ai_pipeline.yml`), из-за чего Gemini-видео тихо не обновлялось с 20.08 до фикса 22.08.

**Решение:** перенести compute-слой (все cron-скрипты пайплайна) на постоянный VPS с root-доступом и своим диском. Судьба статики (index.html и т.д. на GitHub Pages) — под вопросом, см. «On the horizon».

## Key learnings & principles

- **SSH-ключ генерируется на этапе заполнения формы (Networking → Add SSH keys), ДО того как известно про capacity** — кнопки «Download private key» / «Download public key» появляются сразу после выбора «Generate a key pair for me», ещё до нажатия финального «Create». При отказе по «Out of capacity» скачанный так ключ окажется от несостоявшегося инстанса.
  - **Правильный паттерн:** сгенерировать и скачать ключ (private + public) один раз, сохранить оба файла. На всех последующих попытках выбирать «Upload public key file (.pub)» или «Paste public key» и подставлять тот же публичный ключ — тогда при первом успешном создании инстанса private key уже готов и не меняется от попытки к попытке.
- **Home Region в Oracle Free Tier выбирается один раз навсегда** — нет пути назад, решение принимать осознанно на первом же прохождении формы.
- **Verification-ссылка на email при регистрации Oracle живёт ограниченное время и одноразовая** — при повторных попытках регистрации легко случайно открыть устаревшее письмо вместо самого свежего; при повторных попытках регистрации сначала удалять/игнорировать старые письма Oracle, переходить только по ссылке из последнего.
- **Oracle флагает регистрации как подозрительные при повторных прерванных попытках** — экран «К сожалению, при создании вашей учётной записи произошла ошибка» с причинами (a/b/c) появляется в том числе при паттерне «несколько попыток с тем же email/картой», даже если сама карта успешно верифицирована. В этой ситуации повторные клики «Повторить попытку» усугубляют, а не решают проблему — штатный путь — тикет/чат поддержки Oracle.
- **Ценовой трюк CityHost и подобных хостеров:** headline-цена «от X грн/мес» обычно требует предоплаты на максимальный срок (36 мес); реальная помесячная цена — то, что зачёркнуто рядом. При сравнении хостингов всегда смотреть на реальный month-to-month тариф, а не на «от».
- **Hetzner Cloud:** без минимального контракта, счёт выставляется по факту (почасовая ставка, но не выше месячного потолка), Украина явно в списке стран для биллинга — надёжный fallback, если Oracle не взлетит.
- **Корень сегодняшних архитектурных проблем (гонки пушей, недоступные логи, git-как-БД)** — структурная особенность GitHub Actions (эфемерные раннеры без диска), не лечится в рамках текущей архитектуры. Отсюда и решение переезжать, а не патчить симптомы.
- **allowed_domains в песочнице Claude — это HTTP(S)-фильтрующий прокси по доменному имени, не универсальный TCP-firewall.** SSH и другой сырой TCP через него не проходит независимо от того, что в списке — IP или домен. Единственный рабочий паттерн для удалённого управления сервером — HTTP(S)-эндпоинт на самом сервере (свой агент + TLS), который затем добавляется в allowed_domains как обычный домен. Это применимо к любому будущему VPS/серверу, не только к текущему.
- **`nip.io` — бесплатный wildcard DNS-трюк**: `<IP-с-дефисами-вместо-точек>.nip.io` резолвится ровно в этот IP без регистрации домена, этого достаточно для Let's Encrypt (которому для сертификата нужно доменное имя, а не голый IP).
- **Oracle VCN security list по умолчанию (wizard «Create VCN with internet connectivity») открывает только порт 22** — под HTTP(S)-сервисы (80/443) нужно добавлять Ingress Rules вручную в консоли Oracle, это не то же самое, что ufw/iptables на самой машине (два независимых уровня фильтрации).
- **Настраиваемый network egress allowlist в Claude — функция только Team/Enterprise тарифа.** На индивидуальных тарифах (Free/Pro/Max) в Settings → Capabilities есть только вкл/выкл переключатель для доступа к фиксированному списку пакетных менеджеров (GitHub, npm, PyPI, crates.io и т.п.), без возможности добавить свой домен. Это значит: любая архитектура, которая предполагает, что Claude сам стучится HTTP(S) на произвольный внешний сервер/домен, не заработает без апгрейда тарифа. Рабочая альтернатива — обратная схема: внешний сервер сам, по расписанию, стучится на уже разрешённый домен (в нашем случае `api.github.com`) и забирает/кладёт данные (см. `scripts/vps_github_bridge.py`).
- **Мобильный браузер + Oracle Cloud Shell: SSH-сессия внутри Cloud Shell регулярно рвётся** (переключение приложений на телефоне сбрасывает WebSocket-соединение Cloud Shell). Из-за этого нельзя полагаться на многошаговый интерактивный ввод (например, скрытый ввод пароля/токена по запросу скрипта) — сессия может оборваться ровно в момент ожидания ввода. Рабочий паттерн: заранее подготавливать все секреты как часть одной непрерывной команды (`echo 'TOKEN=...' | sudo tee ...` до запуска основного скрипта), избегая любых интерактивных `read` в процессе выполнения на мобильном Cloud Shell.
- **Установка crontab через `install.sh` при обрыве SSH-сессии может не дойти до последней команды**, при этом все предыдущие шаги (пакеты, файлы, токен) уже успешно выполнены — визуально это выглядит как «скрипт завис на предпоследнем шаге». Диагностика: `sudo crontab -l` — если пусто, доустановить cron-строку отдельной командой, не перезапуская весь install-скрипт заново (он идемпотентен для токена/файлов, но лишний прогон `apt-get`/`pip install` тратит время зря).

**Открытый архитектурный вопрос (поднят Русланом 28.08.2026, отложен по его решению):** сейчас `vps_pipeline.py` — один процесс на cron каждые 15 минут, который делает ВСЁ последовательно (проверка моделей, calc_weights, update_local, pws_sync, pws_calibration, marine_history, nearby_precip, hmcbas_telegram). Руслан считает, что каждый под-пайплайн должен жить на своём отдельном cron-расписании, а не быть завязан на один общий 15-минутный тик. Технический нюанс при реализации: если разные под-пайплайны получат отдельные cron-задачи и каждая будет сама делать `git commit`/`push` в один и тот же локальный репозиторий — это **воссоздаст ровно ту же гонку git**, на исправление которой ушёл весь сегодняшний день (только уже между процессами внутри VPS, а не VPS-vs-GH-Actions). Предложенное чистое решение (не реализовано, ждёт решения): разделить "вычисление данных" и "запись в git" — каждый под-пайплайн на своём cron пишет только файлы на диск, без единого git-вызова; отдельный лёгкий "коммитер"-процесс (можно тот же облегчённый `vps_pipeline.py`) работает часто (напр. раз в 5 мин) и просто синкает + коммитит + пушит любые накопившиеся изменения разом. **Решение на сейчас: оставить cron как есть**, вернуться к этому вопросу отдельно.

### Удобный снимок состояния VPS с телефона (реализовано 29.08.2026)

Раньше единственный способ посмотреть диагностику VPS с телефона — Oracle Cloud Shell (SSH внутри веб-консоли), неудобно на мобильном. Теперь у `vps_agent.py` есть отдельный `GET /snapshot` эндпоинт: собирает на сервере всё то же самое, что раньше вручную дёргалось через SSH one-liner (диск, память, сеть, cron, статус сервисов, верхний уровень репо, хвост логов пайплайна и моста, uptime), и отдаёт готовый текст одним запросом.

- **Токен можно передавать как query-параметр** `?token=...` (а не только заголовком `Authorization: Bearer`) — специально, чтобы ссылку можно было просто открыть в браузере телефона или одной командой `curl` из Termux, без ручного проставления заголовков.
- **Форматы:** `format=text` (по умолчанию, для `curl`/терминала) и `format=html` (тёмная монопространственная страница для браузера).
- Из Termux одной строкой:
  ```
  curl -s "https://130-61-25-212.nip.io/snapshot?token=E3a9g7DCHHxsAfhpIhfO_iR0lMVs3Mb66K2uPhQUm9U"
  ```
- В браузере (телефон/десктоп):
  ```
  https://130-61-25-212.nip.io/snapshot?token=E3a9g7DCHHxsAfhpIhfO_iR0lMVs3Mb66K2uPhQUm9U&format=html
  ```
- Удобно завести алиас в Termux (`~/.bashrc` или `~/.zshrc`): `alias vpsstatus='curl -s "https://130-61-25-212.nip.io/snapshot?token=E3a9g7DCHHxsAfhpIhfO_iR0lMVs3Mb66K2uPhQUm9U"'`.
- **Проверено полным циклом 29.08.2026, включая исправление реальной проблемы.** Первая попытка открыть ссылку с телефона не сработала вообще — не hairpin NAT (ошибочная первая гипотеза Claude), а **порты 80/443 были заблокированы локальным iptables на самой VPS** (`Chain INPUT`, явно разрешён только 22, всё остальное падало в финальный `REJECT`). Из-за этого Caddy ни разу не мог пройти HTTP-01/TLS-ALPN-01 челлендж Let's Encrypt с момента установки агента (26.08.2026) — попытки шли на staging-CA каждые 6 часов и тихо проваливались, сертификат никогда не был реально выпущен. **Фикс:** `sudo iptables -I INPUT 4 -p tcp -m state --state NEW -m multiport --dports 80,443 -j ACCEPT` + `netfilter-persistent save` (переживает перезагрузку) → `systemctl restart caddy` → боевой сертификат выпущен с первого раза. После фикса `curl https://130-61-25-212.nip.io/health` **с самого сервера тоже вернул 200** — значит hairpin NAT в этом облаке не блокирует обратный доступ на свой же публичный IP, версия про NAT была в принципе неверной. Пункт старого чек-листа «Проверить security list VCN» на самом деле упирался в этот локальный iptables, а не в Oracle-уровневый security list — теперь закрыт.
- **Проверено изнутри сервера через `curl http://127.0.0.1:8080/snapshot?token=...` — работает корректно.**
- **Биллинг/остаток триал-кредита Oracle сознательно не включён в снапшот.** Проверка через API требует OCI CLI + tenancy-level API-ключи (уже существуют как GitHub Secrets для `oci_capacity_retry.py`), но размещать их на самом VPS означало бы держать ключ уровня tenancy на сервере, который и так торчит наружу HTTP-эндпоинтом — сознательно решили не расширять поверхность атаки ради удобства. Что фактически контролирует расходы: жёсткие лимиты Always Free (shape `VM.Standard.A1.Flex`, ≤2 OCPU/≤12GB RAM, ≤200GB volume суммарно, единственный instance) — уже задокументированы выше и не менялись; пока их не превышать, счёт не растёт независимо от того, смотрим мы биллинг-дашборд или нет. Если понадобится — можно поднять вопрос отдельно (например, выделенный voice-only OCI CLI на VPS с ключом, ограниченным только на read billing/usage, без прав на управление ресурсами).

**Порядок ротации:**
1. Сгенерировать новый PAT на GitHub (тот же scope: repo + workflow).
2. Сначала обновить `~/.git-credentials` (через bridge — он ещё работает на старом токене, т.к. сам мост читает файл (2), а не (1)).

### Гарантии бесплатного тарифа (обязательно проверять на каждом шаге)

- **OCI Always Free:** shape VM.Standard.A1.Flex, ≤2 OCPU/≤12GB RAM, boot+block volume ≤200GB суммарно — уже утверждено, не менять без явного обсуждения.
- **Не хранить на VPS ничего лишнего:** shallow-клон, не полная история; ротация/очистка логов (`/var/log/vps-github-bridge.log`, будущие логи пайплайна) — не давать расти бесконтрольно.

## Approach & patterns

- Регистрация и первичная настройка VPS — интерактивно, по скриншотам от Руслана; Claude подтверждает следующий шаг и заранее предупреждает о необратимых решениях (регион, shape инстанса, образ ОС) до того, как они будут приняты.
- При сбоях в процессе регистрации — не рекомендовать слепые повторные попытки, сначала диагностировать вероятную причину (устаревшая ссылка, антифрод-флаг и т.п.).
- После получения VPS — Claude сможет выполнять реальные команды на сервере (SSH), но только после того как Руслан добавит IP/домен сервера в network settings Claude (тот же паттерн, что и с GitHub PAT, только теперь для живого сервера).
- Как и с репозиторием — Claude работает с сервером напрямую сам, без участия Руслана в Termux/консоли, кроме шагов, требующих его физического подтверждения (оплата, выбор в веб-форме до выдачи Claude доступа).
