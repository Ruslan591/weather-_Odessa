# Тема: Open-Meteo — бюджет запросов, лимиты, инциденты 429

_Последнее обновление: 2026-09-08_

## Ключевой вывод (из живого инцидента + прошлого опыта)

Open-Meteo лимитирует в первую очередь ЧАСТОТУ запросов (залпы без пауз),
а не суммарный объём точек в одном запросе и не суточный/часовой тотал —
у нас daily/hourly тоталы (~2000/сутки) далеко от документированных
5000/час, 10000/день, но 429 всё равно ловим, когда несколько скриптов
(или один скрипт дважды) стучатся почти одновременно без пауз.

## Все потребители Open-Meteo на VPS (по состоянию на 2026-09-08)

| Скрипт | Функция | Запросов | Пауза | Когда срабатывает |
|---|---|---|---|---|
| `update.py` (через `update_local.py`, вызывается из `vps_pipeline.py`) | `fetch_ensemble_ready_time()` | 6 (meta.json, у 2 из 8 моделей нет metaId) | **нет** | безусловно, каждый раз при вызове `update_local.py` |
| `update.py` (тот же вызов) | `fetch_forecast_model()` ×8 | 8 (v1/forecast) | 0.5с | только если `need_synop`/`need_pws` (новый прогон ансамбля готов) |
| `open_meteo_frontal_confirm.py` | `fetch_model_batch()` ×5 | 5 (v1/forecast) | 30с (проверено вживую 2026-09-06) | только по новому прогону модели (`_has_new_model_run`, читает `model_runs_history.json`) |
| `vps_pipeline.py` | `fetch_run_time_and_interval()` | 1 на модель | — | только когда реально "пора" (`next_expected`, с 29.08.2026 не сеть каждый цикл) |

`update_local.py` вызывается из ДВУХ независимых мест внутри одного цикла
`vps_pipeline.py`, которые **не знают друг о друге** — см. инцидент ниже.

## Инцидент 2026-09-07: 429 у open_meteo_frontal_confirm.py

**Симптом:** в 15:17:58 UTC `open_meteo_frontal_confirm.json` записался с
`n_models: 0` у ВСЕХ кандидатов — то есть отвалились все 5 запросов
(включая встроенный ретрай на 429).

**Расследование** (по `journalctl`, `/var/log/vps-pipeline.log`,
`/var/log/vps-satellite-pipeline.log` — реальный crontab и логи
прочитаны напрямую с VPS через Termux, не по предположениям):

1. Реальный crontab: `vps_pipeline.py` (`*/5`), `vps_satellite_pipeline.py`
   (`2,7,12,17,...`), `vps_ai_pipeline.py` (`4,9,14,19,...`),
   `vps_github_bridge.py` (`* * * * *`). Отдельного cron-задания на
   `update_local.py`/`update.py` НЕТ — вызывается сабпроцессом изнутри
   `vps_pipeline.py`.
2. **ВАЖНО:** `vps_pipeline.py` печатает заголовки циклов в ЛОКАЛЬНОМ
   времени (`iso_to_local`, Europe/Kyiv), `vps_satellite_pipeline.py` —
   в UTC (`'%d.%m %H:%M UTC'`). При сверке логов по времени инцидента
   (UTC, из git-таймстампа) это нужно учитывать — на этом сам споткнулся
   в процессе разбора, пересчитывая местное/UTC.
3. Цикл `vps_pipeline.py` в 18:15 местного (=15:15 UTC, найдено в
   `/var/log/vps-pipeline.log`, строка ~201675) — ровно за 2мин58с до
   429 — показал РЕДКОЕ совпадение:
   - у GRAPES как раз подоспел новый прогон → `run_pipeline()` вызвал
     `update_local.py --no-model` как штатный шаг
   - **в этот же самый момент** час 15 — synop-час (`SYNOP_HOURS_UTC`),
     минута 15 внутри окна 11-21 → `is_synop_window()` тоже сработало →
     `update_local.py --no-model --no-fill` вызвался ВТОРОЙ раз в том же
     цикле
4. `update_local.py::main()` вызывает `_upd.main()` (`update.py`)
   БЕЗУСЛОВНО — флаги `--no-model`/`--no-fill` подменяют только шаги
   0/2 (`fill_modeldata`/`fetch_historical_model`) через monkey-patch, а
   `fetch_ensemble_ready_time()` (6 запросов без паузы) внутри `_upd.main()`
   вызывается ВСЕГДА, независимо от флагов.
5. Итог: **~12+ запросов к Open-Meteo слепленных в течение ~минуты**, без
   координации между двумя вызовами. Через 2м58с после этого
   `open_meteo_frontal_confirm.py` (5 запросов, честно с паузой 30с)
   попал под всё ещё действующий rate-limit.

**Фикс (2026-09-08, `vps_pipeline.py`):** флаг
`ran_update_local_this_cycle` — если `run_pipeline()` уже вызвал
`update_local.py` в этом цикле (был новый прогон модели), SYNOP-ветка
`update_local.py` в том же цикле пропускается (данные и так только что
проверены). Убирает дублирование полностью, оставляя нормальную частоту
для обоих независимых условий срабатывания.

## Фикс 2026-09-08: запас 30% в планировании проверок прогонов

Отдельная, более тонкая находка (не сама причина 429, но смежная —
могла приводить к пропуску прогонов в истории, см. неполные дни в
"История прогонов" на `nearby.html`/Точность):

`vps_pipeline.py::next_expected` считался как `last_run + interval_sec`
БЕЗ запаса, где `interval_sec` — паспортный `update_interval_seconds` из
meta.json (ICON EU=3ч, остальные 5 моделей=6ч). Реальная задержка
публикации плавает и бывает короче паспортной — проверено по полному
дню истории (06.09.2026, все 6 моделей):

| Модель | Паспортный интервал | Реальный минимальный | Отклонение |
|---|---|---|---|
| ICON EU | 180 мин | 127 мин | -29.4% |
| ECMWF IFS | 360 мин | 298 мин | -17.2% |
| UKMO | 360 мин | 299 мин | -16.9% |
| Arpège | 360 мин | 315 мин | -12.5% |
| GRAPES | 360 мин | 325 мин | -9.7% |
| GFS | 360 мин | 359 мин | -0.3% |

Без запаса — если СЛЕДУЮЩИЙ (тоже ранний) прогон выходит раньше
запланированной проверки, он молча теряется из
`model_runs_history.json`. Добавлена константа
`SCHEDULE_MARGIN_FRACTION = 0.30` — `next_expected = last_run +
interval_sec * 0.70`. Перекрывает худший наблюдённый случай (ICON EU) с
небольшим допуском, для остальных моделей — щедро. Стоимость — несколько
лишних лёгких meta.json-проверок на прогон, некритично на фоне бюджета
запросов (см. таблицу потребителей выше).

## На горизонте

- Пользователь подтвердил: расширять объективную линию фронта на
  far/very_far (Европа-Атлантика) через поле давления Open-Meteo —
  ОДНОЗНАЧНО ДА (см. `frontal_line_stations.md`). Это добавит ЕЩЁ один
  независимый потребитель Open-Meteo (~5 запросов на событие, отдельный
  event-гейт по новому прогону модели, отдельный бюджет точек ~165 при
  шаге сетки 300км) — решение по шагу сетки (300км vs 200км) не принято
  пользователем, отложено до стабилизации текущих проблем с 429.
- Стоит рассмотреть общий "трафик-менеджер"/семафор на уровне VPS,
  единый для ВСЕХ скриптов, дёргающих Open-Meteo — сейчас каждый скрипт
  независимо решает, когда ему можно стучаться, что и привело к
  сегодняшнему инциденту. Не реализовано, идея зафиксирована для
  дальнейшего рассмотрения при добавлении far/very_far.
