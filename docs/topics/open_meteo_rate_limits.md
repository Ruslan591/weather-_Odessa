# Тема: Open-Meteo — бюджет запросов, лимиты, инциденты 429

_Последнее обновление: 2026-09-08_

## Ключевой вывод (из живого инцидента + прошлого опыта)

Open-Meteo лимитирует в первую очередь ЧАСТОТУ запросов (залпы без пауз),
а не суммарный объём точек в одном запросе и не суточный/часовой тотал —
у нас daily/hourly тоталы (~2000/сутки) далеко от документированных
5000/час, 10000/день, но 429 всё равно ловим, когда несколько скриптов
(или один скрипт дважды) стучатся почти одновременно без пауз.

## Все потребители Open-Meteo на VPS (по состоянию на 2026-09-08)

| Скрипт | Функция | Запросов | Пауза | Когда срабатывает |
|---|---|---|---|---|
| `update.py` (через `update_local.py`, вызывается из `vps_pipeline.py`) | `fetch_ensemble_ready_time()` | 6 (meta.json, у 2 из 8 моделей нет metaId) | **нет** | безусловно, каждый раз при вызове `update_local.py` |
| `update.py` (тот же вызов) | `fetch_forecast_model()` ×8 | 8 (v1/forecast) | 0.5с | только если `need_synop`/`need_pws` (новый прогон ансамбля готов) |
| `open_meteo_frontal_confirm.py` | `fetch_model_batch()` ×5 | 5 (v1/forecast) | 30с (проверено вживую 2026-09-06) | только по новому прогону модели (`_has_new_model_run`, читает `model_runs_history.json`) |
| `vps_pipeline.py` | `fetch_run_time_and_interval()` | 1 на модель | — | только когда реально "пора" (`next_expected`, с 29.08.2026 не сеть каждый цикл) |

`update_local.py` вызывается из ДВУХ независимых мест внутри одного цикла
`vps_pipeline.py`, которые **не знают друг о друге** — см. инцидент ниже.

прочитаны напрямую с VPS через Termux, не по предположениям):

3. Цикл `vps_pipeline.py` в 18:15 местного (=15:15 UTC, найдено в
   `/var/log/vps-pipeline.log`, строка ~201675) — ровно за 2мин58с до

     `update_local.py --no-model --no-fill` вызвался ВТОРОЙ раз в том же
     цикле
4. `update_local.py::main()` вызывает `_upd.main()` (`update.py`)

**Фикс (2026-09-08, `vps_pipeline.py`):** флаг
`ran_update_local_this_cycle` — если `run_pipeline()` уже вызвал
`update_local.py` в этом цикле (был новый прогон модели), SYNOP-ветка
`update_local.py` в том же цикле пропускается (данные и так только что
проверены). Убирает дублирование полностью, оставляя нормальную частоту
для обоих независимых условий срабатывания.

## Важная поправка 2026-09-09 — не всё, что выглядит как 429, это 429

08.09 поймали ещё один сбой всех запросов европейского детектора и по
инерции приняли его за очередной 429 (коллизию скриптов). При разборе
по живому логу оказалось — это **HTTP 414 "Request-URI Too Large"**,
причина совершенно другая (слишком длинный URL из-за неокруглённых
координат, не частота запросов) — см. подробный разбор в
`frontal_line_stations.md`. Урок: при новом сбое ВСЕГДА проверять
реальный код ответа в логе, а не сразу применять диагноз от прошлого
похожего на вид инцидента — разные HTTP-коды означают разные причины,
даже если внешне ("все 5 запросов отвалились") выглядит одинаково.

### modelData vs ensemble-снимки — два независимых потока в update.py

## GPT REQUEST CHANGES — исправлен discovery-scheduling для stale meta.json (2026-09-12)

**Причина 5-минутного polling stale-модели:** `next_expected` в `vps_pipeline.py` при `is_same_run=True` всегда пересчитывался как `last_run + effective_interval` — то есть от неизменного `run_time`. Для GEM Global (`run_time` не менялся с мая) это значение навсегда осталось в прошлом → `due=True` каждый 5-минутный цикл бессрочно ("без дедлайна" — было явно заложено в докстринге как намеренное поведение для здоровых моделей, ожидающих скорой публикации).

**Что изменено:** добавлен общий backoff (не GEM-specific) — если модель просрочена больше чем в `STALE_BACKOFF_MULTIPLIER=3` раза от собственного `update_interval_seconds`, следующая проверка планируется через `STALE_RECHECK_SEC=6ч` от текущего момента вместо пересчёта от `run_time`. Применяется только при `is_same_run=True`.

**Почему не задерживает нормальное обнаружение:** порог (3× интервала — для GEM это 36ч, для 6-часовых моделей 18ч) заметно больше типичной задержки публикации; активный 5-минутный опрос вблизи ожидаемого времени сохраняется без изменений, пока модель не просрочена настолько сильно, что это уже явно "застряла", а не "чуть задержалась".

**Тест (синтетика, без сети):**
- GEM Global, run_time 2026-07-01, interval 12ч, now=2026-09-12 → просрочка ~1751ч (≫36ч) → BACKOFF, next_expected = now+6ч, due-через-5мин=False.
- ECMWF с типичной задержкой публикации 8ч на 6-часовом интервале (≪18ч) → normal active-poll, due-через-5мин=True — как и раньше.
- Только что обнаруженный новый run (is_same_run=False) → backoff не применяется, next_expected обычный.

**Дополнительно (найдено при реализации, вне первоначального ТЗ):** `merge_ensemble()` был переписан с index-based на time-based выравнивание — при позиционном слиянии кэш с чужим (сдвинутым) time-axis тихо смешивал бы данные разных календарных дней. Добавлена также `min_time`-отсечка (now−6ч) в `merge_ensemble()`, чтобы протухший кэш (GEM) не протаскивал в снимок осиротевшие записи с датами из прошлого. Оба фикса покрыты synthetic-тестами (без реальных HTTP-вызовов, т.к. `api.open-meteo.com` недоступен из песочницы).
