# VPS: чистка диска (2026-09-16)

## Проблема
Диск VPS вырос до 13G/45G (30%). Причина: `.git` на VPS = 7.2G из 13G.

## Причина роста .git
Локальный клон на VPS — **shallow** (несмотря на то что `git rev-parse
--is-shallow-repository` иногда возвращает `false` после операций вроде
`git-filter-repo` — это артефакт перезаписи, не признак полного клона).
Реальная история `origin/main` на GitHub — ~36 900 коммитов (проверено
через Link-заголовок пагинации `commits API`, `per_page=100` → `page=370`).

Внутри shallow-окна на VPS накопились:
1. `data/blocks_gemini/tmp/` — кадры рендера видео (аналог уже
   игнорируемого `data/blocks/tmp/`, но для gemini-ветки забыли добавить
   в `.gitignore`).
2. 32 файла внутреннего состояния/диагностики спутникового пайплайна
   (`eumetsat_*_buffer.npz`, `*_debug.json`, `*_state.json`, растущие
   `*.jsonl`-логи) — коммитились каждые 5 минут (288 раз/сутки),
   не читаются фронтендом (проверено grep по `eumetsat.js`/
   `nearby_precip.js` + code-search по репо).

## Что сделано
1. `.gitignore`: добавлены `data/blocks_gemini/tmp/` и 32 пути выше.
2. `git rm --cached` для файлов, которые были фактически затрекан на
   момент чистки.
3. **НЕ делал** `git-filter-repo` + force-push в `main` — это было бы
   ошибкой: локальный клон видел только ~16-20 коммитов (shallow), и
   force-push обрезал бы `origin/main` до этой глубины, уничтожив
   ~36 884 реальных коммита истории. Если понадобится реально почистить
   ИСТОРИЮ на GitHub (не только VPS-диск) — нужен **полный** clone
   (`git clone` без `--depth`, вероятно тяжёлый) и осторожный
   filter-repo на нём, отдельная задача с бэкапом.
4. Вместо этого: старый раздутый `.git` на VPS просто заменён свежим
   shallow re-clone (`git clone --depth 20`). GitHub не тронут, риска
   ноль. `.git`: 7.2G → 99M. Итог по диску: **13G → 6.2G (30% → 15%)**.
5. Нетрекаемые файлы состояния пайплайна (open-meteo cooldown/rate-limit,
   scratch pixel-map'ы для детекции изменений, `model_next_expected.json`)
   сохранены и перенесены в новый клон вручную (их нет в git, живут
   только на диске VPS).

## Найденный баг инфраструктуры (НЕ починено, нужен отдельный проход с GPT)
`sync_repo()` / `_preserve_unpushed_local_commits()` (продублирована в
`vps_pipeline.py`, `vps_satellite_pipeline.py`, `vps_ai_pipeline.py`,
добавлена 2026-09-14, "ROOT CAUSE ORPHANED OBJECTS v2") делает
`git fetch origin main --depth 1 --update-shallow` регулярно. На
практике поймали случай: после свежего `--depth 20` clone этот
`--depth 1` рефетч сдвинул shallow-границу и разорвал связность графа —
`git rev-list --count origin/main..HEAD` увидел "20 локальных коммитов"
там, где реальной расходимости не было. Сработал `_preserve_unpushed_
local_commits()` → `git push origin HEAD:main` (rejected, non-fast-
forward) → `git rebase -X theirs origin/main` — и в результате этого
реплея **`.gitignore` откатился к версии ДО наших правок** (32 файла
и `data/blocks_gemini/tmp/` пропали из игнора, кто-то из пайплайнов
тут же закоммитил их обратно).

Пофиксили откат вручную (см. выше), но сам механизм остаётся хрупким:
периодический `--depth 1 --update-shallow` может и дальше рвать shallow-
граф при определённых условиях гонки между тремя параллельными cron-
процессами. Возможные направления фикса (не реализовано, нужно
обсудить с GPT перед кодом):
- не форсировать `--depth 1` при каждом fetch, а использовать
  `--update-shallow` без явного `--depth`, чтобы не пересобирать
  границу с нуля каждый раз;
- либо явно фиксировать бОльшую глубину (`--depth 50/100`) с запасом.

## Побочные находки
- `git add` в `git_push_satellite()` НЕ использует `-f` — `.gitignore`
  работает штатно для новых файлов. Повторное появление файлов в
  трекинге происходило либо (а) в окне до того как локальный клон
  подтянул обновлённый `.gitignore`, либо (б) через откат
  `_preserve_unpushed_local_commits()` (см. выше) — не через force-add.
- `git rm --cached` падает на ВЕСЬ список, если хотя бы один путь не
  найден — использовать `--ignore-unmatch`.
- Bridge (`vps_github_bridge.py`) сам коммитит `data/vps_result.json` —
  это может увести `origin/main` вперёд между `git fetch` и `git push`
  в других задачах, обычный `rebase`/`fetch` перед push решает.
- `crontab -r` стирает ВЕСЬ crontab пользователя, а не отдельные
  строки — для выборочной паузы использовать `grep -v` перед перезаписью.
  Ещё: bridge и три пайплайна должны жить в crontab **root** (токен
  бриджа читается только root'ом), не в crontab текущего SSH-юзера.
